# src-tauri — Backend (Rust + Tauri v2)

## Purpose

The Rust backend: low-level keyboard capture, Razer-encoding detection, action execution (keystrokes, mouse, text/snippets, sequences, launches), config persistence with backups/recovery, Synapse import, the mouse's own onboard button memory, window/foreground resolution, and the Tauri IPC surface.

## Ownership

- `src/lib.rs` — Tauri app setup + the `#[tauri::command]` handlers (the IPC surface called from `src/lib/backend.ts`).
- `src/config.rs` — `AppConfig`, load/save, schema + semantic validation, atomic writes, rolling/daily backups, corrupt-recovery + newer-schema guard.
- `src/executor.rs` — runs actions; `src/input_synthesis.rs` — `SendInput` keystroke/mouse/text, clipboard paste, snippet-token expansion.
- `src/backup.rs`, `src/resolver.rs`, `src/window_capture.rs`, `src/hotkeys.rs`, `src/vk.rs`, `src/chord.rs`, `src/recorder.rs`.
- `src/device_catalog.rs` — one `NativeModel` descriptor per natively driven mouse (VID/PIDs, transaction byte, key-button ids, vendor slots, native buttons, DPI range, poll codes); `CATALOG` lists them: `NAGA_V2_HYPERSPEED` and `NAGA_V3_PRO` (verified) and `NAGA_V2_PRO`, `NAGA_PRO`, `NAGA_X` (unverified, data from openrazer + Synapse's button table; test `only_the_hardware_tested_models_are_verified` pins the list). Each model names its config `device_id` (`razer-naga` for the V2 family, `razer-naga-v3`) and `control_prefix` (`v3_`), its `Transport` (`Onboard`: persistent records in onboard profile 1 kept by the guard; `LiveOverlay`: only the reversible live map) and an optional `LiveSpec` (extra controls, firmware HyperShift button, onboard banks, display-name keys) that drives `live_overlay`. Nothing else branches on a model: add a model by adding its entry. Each model names its vendor USB `interface`: the registry leaf must contain `VID_…&PID_…&MI_<interface>` (`interface_needle`/`interface_path`; `3` on the Naga X). Model-specific values live here, never as constants in `mouse_memory.rs`. `consumer: Some(ConsumerSignals)` (V2 HyperSpeed per key button, test `consumer_usages_cover_every_key_button_once`; a live-overlay model takes its usages per control and layer from `live_overlay::USAGES`) gives each key button a reserved consumer usage and names the collection that carries the reports (`MI_01&Col03`, report id `0x02`). `verified: false` (a model not yet proven on hardware), or a `LiveOverlay` transport, makes `VendorDevice::require_verified` refuse every onboard-profile write that changes a button — `write_button`, `write_record`, `restore_native_button`, `ensure_normal_mode` — so such a model is only read and gets DPI/poll writes; the guard only reports its battery (`Verdict::ReadOnly`) and no offline profile is written or restored for it. Windows-only. Adding and verifying a model: `docs/ADDING-A-MODEL.md`; roadmap: `plans/multi-device/plan.md` (local).
- `src/mouse_settings.rs` — independent nullable live readings, per-field keyed warnings, complete/partial/unavailable/disconnected status, public error redaction and summary/full report formatting. A failed secondary reading cannot turn a confirmed setter into failure; open failure and no device are distinct.
- `src/mouse_memory.rs` — the mouse's vendor HID collection: opens it, writes a button record into its onboard slot and verifies the mouse's echo (`apply_onboard_mapping`, `verify_onboard_mapping`), reads the device mode and the stored per-button records, and puts the mode back to `Normal` (`restore_onboard_control`). Windows-only (`#[cfg(target_os = "windows")]` on the module).
- `src/mouse_offline.rs` — the offline profile: on exit (`shutdown_mouse`, from `RunEvent::Exit` or the end of the Windows session) the chosen profile (`Settings.offline_profile_id`: absent = the fallback profile, `OFFLINE_PROFILE_ACTIVE` "@active" = the one in effect — which follows the focused window, so it is not the default) is written into the mouse so its single-key and mouse-button bindings work without Sidearm (layer 1 + firmware Hypershift on the trigger when the profile has playable hypershift bindings); a marker file makes the guard put Sidearm's signals back on the next start. Windows-only.
- `src/mouse_restore.rs` — the restore process a dead Sidearm leaves (`--restore-live-maps`), the named mutexes (`Local\Sidearm-app`, `Local\Sidearm-live-map-restore`, `claim_app`) and the elevated relaunch wait. Windows-only.
- `src/mouse_speed.rs` — each profile's DPI / poll rate written live on a switch, DPI Up/Down stepping, and the speed a switch replaced (`Originals`) for the exit to put back. Windows-only.
- `src/onboard_guard.rs` — the takeover watchdog: while the runtime is active it polls the device mode and the stored thumb records, puts them back when Razer's engine changed them, and reports it as `onboard_takeover` (throttled per kind, `NOTIFY_COOLDOWN`). Windows-only.
- `src/synapse_control.rs` — explicit Razer application ownership transfer, validated process paths, and reversible per-user Synapse startup changes. Never touches services/drivers. Startup backups are bound to the Windows computer and logon user returned by Win32; only the exact HKCU Run/RazerAppEngine entry is supported, with original type/bytes preserved and read-back checked. Unknown startup mechanisms require Windows Startup apps. Process-list failure is unknown, not absence. The IPC recovery checks the runtime and verified mouse before closing Razer, restores/read-checks onboard settings through the shared restore helper, restarts capture, then optionally changes startup; partial startup failure is returned separately. Physical input still requires the user's test.
- `src/mouse_status.rs` — what the user must know about the mouse path that is not a takeover, emitted as `mouse_status` `{kind, active}` and kept for a window that opens later (`get_mouse_status` → `snapshot`): **states** held until cleared (`helperLost` — the capture helper died and was not restarted; `buttonsUnreadable` — the consumer reader cannot open its collection; `mouseUnreachable` — the guard failed for `UNREACHABLE_AFTER`, an asleep or absent mouse excluded — `Verdict::Asleep`/`Absent`, `mouse_memory::NOT_CONNECTED`; both states are cleared while the runtime is stopped) and one-time **notices** taken by the first snapshot (`offlineNotStored` — the last exit left `mouse-offline-failed`; `signalsSwitched` — the guard rewrote the key buttons to the configured signal kind). Windows-only.
- Manifests: `Cargo.toml`, `tauri.conf.json`, `capabilities/` (under src-tauri). The config JSON schema is `schemas/config.v5.schema.json` at the repo ROOT, bundled into `config.rs` via `include_str!("../schemas/...")`.
- `src/menu_popup.rs` — the live popup of a `menu` action: `Model` (pure, unit-tested: the top level shows its submenus as **blocks** — a heading over their items, inline, numbers running on through all blocks — a submenu inside a block opens as its own level; a search shows every enabled action of the tree whose name or sent text matches; highlight, back) and the `menu` window (`public/menu.html` + `menu.js`, created on first open, transparent around the list and the tip, capability `capabilities/menu.json`). The popup takes the keyboard focus (`set_focus`) so typing searches, arrows/Enter pick and Esc closes without reaching the app; picking or closing from the menu gives the focus back to the window it opened over (`restore_foreground`) before the item runs; a click elsewhere or another window in front just closes it (watcher thread; also after 60 s). The page draws the `View` Rust emits (`menu-show`, with `placeholder`/`empty` from `backend.menu.*`), measures itself (`menu_layout`, in physical pixels at its own `devicePixelRatio`, again on a resize or scale change — a fresh window still on another monitor was cut off when Rust multiplied CSS pixels by the target's scale) and forwards input (`menu_hover` only on real pointer movement, `menu_pick`, `menu_back`, `menu_wheel`, `menu_search`, `menu_confirm`, `menu_close`); Rust sizes it and places it at the cursor (`display::position_near`). Pinned action items (`MenuItem.pinned`) come first in a ★ block and only there. A search also looks through every other menu (`Model::with_others`, grouped under the menu's name, links to menus skipped, an action found once). After 600 ms on a phrase the tip asks `menu_full_text { index }` for its whole text and widens, PageUp/PageDown scroll it. Each item carries `detail`, what it sends (`action_detail`), or for a submenu `children`, the rows of its level (one per line, pinned ones left out), shown in the tip beside the highlighted row so the list never changes shape under the pointer; a click on one of them takes it directly (`menu_pick_child { index, child }` → `Model::pick_child`). The picked item runs through `capture_backend::run_menu_item` on the opening press's profile/control/layer; an item whose action is another menu opens that menu in place of this one (same opening button, so its press closes it), so menus may link to each other — `validate_config` rejects only an item opening its own menu; a right click on a phrase offers `PickMode` Run / Enter (run, then Enter after 80 ms) / Copy (its whole text into the clipboard, nothing typed; `menu_pick { index, mode }`) and, on a phrase or a list, Edit (`menu_edit { index }`: the menu closes, the main window comes up and gets `menu_edit_requested { menuActionId, itemId, profileId }` — the item's own menu, also for a search hit from another menu). The search also matches a query typed in the other keyboard layout (both sides compared as ЙЦУКЕН/QWERTY keys, `hotkeys::normalize_cyrillic_key`). Every action run is counted per day in `press-log-<computer>.json` next to the config (`src/press_log.rs`; one file per computer, added up when read — `src/machine_files.rs`, so a synced data folder never has two computers rewriting one file; places `profile|layer|control|gesture` and action ids, 90 days, written at most every 15 s and at exit, wheel scrolling left out, `get_press_log`; `export_layout_folder` copies it with the config, `menu-usage.json` and the device photos). Every pick is counted in `menu-usage-<computer>.json` next to the config (per computer, added up; an old `menu-usage.json` is still read) (`src/menu_usage.rs`, `get_menu_usage`; never in the config, so a pick does not rewrite or sync it). A radial look would be another drawing of the same `View` (its config field and schema bump come with it). Fake mode keeps the model and skips the window.
- Delegated to children: `src/capture_backend/`, `src/synapse_import/`, `src/platform/`.

## Local Contracts

- Internal fns return `Result<T, String>`; convert to `CommandError` at the IPC boundary.
- **Text in Rust is English.** The file log (`log::*`, also the UI's log panel) and error strings (`Err(String)`, `CommandError::new`) are plain English. Text the UI shows to the user — runtime log entries (`record_*`, message is `ui_text::UiText`), `RuntimeErrorEvent.message`, execution `summary`/`warnings` — is built with `crate::ui_text!("area.name", "English with {name}", name = value)`: a key under `backend.` in `src/i18n/locales/{en,ru}.json` (`{{name}}` placeholders) plus the English fallback; the frontend renders it with `uiText()` (`src/lib/ui-text.ts`), and `normalizeCommandError` translates a keyed `CommandError::from_ui`. Log categories are English ids (`capture`, `execution`, `resolution`, `runtime`, `windowCapture`, `clipboard`, `textInput`; names in `log.category.*`). The tray and the OSD are drawn by Rust: the frontend sends the current language's `backend.*` texts (`set_native_texts`, at start and on every language change) and Rust uses `ui_text::native(&text)`, which falls back to English. The test `src/lib/ui-text.test.ts` fails when a `ui_text!` key is missing from either locale. Cyrillic stays only where it is data: the ЙЦУКЕН layout table, test fixtures, Synapse's `Макросы` folder, the seeded default snippets.
- Config is schema-first: the bundled `config.v5.schema.json` validates raw JSON before deserialize. A persisted field rename needs `anyOf`(both names) in the schema + `#[serde(alias)]`. Keep the Rust structs, `src/lib/config.ts`, and the schema in sync.
- `config.json` changed outside Sidearm (by hand, a script, a sync) is picked up without a restart: the `config-watch` thread (`spawn_config_watch`) checks its modification time every second, and a content stamp that differs from `ConfigStamp` (which every own save/load updates) and holds for one more poll emits `config_changed_externally` (the UI reloads) and restarts a running capture from disk.
- `read_text_folder` (menu editor "Add from folder"): the `.txt`/`.md` files directly in a user-chosen folder (≤ 1 MiB each, ≤ 200, UTF-8); their text is copied into the config, the folder is never referenced.
- `send_shortcut` releases the modifiers it pressed 30 ms after the key (`MODIFIER_RELEASE_DELAY_MS`), in a second `SendInput`: in one batch they read as up by the time the target handled the key — Windows Terminal (Claude Code in it) typed a bare "v"/"м" for a sent Alt+V (2026-11-12, notebook).
- Config writes are atomic (temp + rename); backups (rolling rotation, daily snapshot, last-known-good) are best-effort and never fail the save. A corrupt `config.json` recovers from last-known-good/rolling backups; a config declaring a newer schema version is never overwritten.
- A Sidearm that starts while another one is exiting waits up to 60 s for it to be gone (`claim_app`: the exit creates `Local\Sidearm-exiting` first thing, `mouse_restore::mark_exiting`). Overlapping, both used one WebView2 data folder (`data\EBWebView`), whose environments share their processes: the new window sometimes never came up and no capture started (e2e scenario 9, red without the wait, measured 2026-11-11).
- "Run as administrator" (`relaunch_as_admin`) starts the elevated Sidearm with `--relaunched`; that process waits up to 60 s for `Local\Sidearm-app` to disappear before it starts (the old one restores its mice on exit, and the single-instance lock would turn the new one away).
- `src/admin_autostart.rs`: the elevated logon task never starts Sidearm.exe directly — it runs System32 PowerShell with a verifier script (in the task XML) that checks SHA-256 of the exe + every sibling `*.dll` pinned at enable time and holds them open until Sidearm is up. Re-running `enable()` re-pins (the "confirm after update" path, `needsReconfirm`). Keep `%` and `"` out of the script. Registering/deleting needs admin: an elevated Sidearm does it in-process; a non-elevated one runs its own exe elevated with `--admin-autostart enable|disable` (`runas`, dispatched in `main.rs` before Tauri starts) and maps the helper's exit code (0 / HRESULT / 1) — never use the `Elevation:Administrator!new:` moniker, Task Scheduler is not registered for it (`CO_E_ELEVATION_DISABLED`). The task XML must stay within its declared schema 1.2 (an unknown element fails registration with 0x80041316).
- Self-injected input carries `INTERNAL_SENDINPUT_EXTRA_INFO`; VK 0xE8 is the mask/probe key (`vk.rs` `VK_MASK_KEY`), deliberately not a modifier. **Every `dwExtraInfo` tag must fit in 32 bits**: a `WH_MOUSE_LL` hook receives it truncated to its low dword (measured: `0x1122334455667788` arrives as `0x55667788`, while a `WH_KEYBOARD_LL` hook sees the full value). A wider tag stops matching in the mouse hook, which then treats our own injected clicks as physical presses and swallows them.
- Takeover guard (`onboard_guard.rs`): a takeover is only ever reported for a mode the guard **read** as non-`Normal` and for stored records it **read** as different from the config. Two rules come from hardware measurement: a mode read-back is retried (`MODE_CONFIRM_ATTEMPTS`) because a `SET Normal` whose read-back still said `Driver` was `Normal` one second later, so a transition must never be reported as a failed takeover; and a drifted record is read twice before it counts, because a read that catches the device mid-transition answers with plausible but wrong bytes. A refused command (an idle/sleeping wireless mouse answers status `0x04` to every vendor query) is not evidence of a takeover — log at debug and wait for the next tick. The guard is silent while `RuntimeStore::is_running()` is false: a stopped Sidearm does not fight Razer for the mouse. It guards every addressable button: the key records (thumbs + top buttons, `onboard_bindings`) and the plain mouse buttons (the model's `native_buttons`: left/right/middle, wheel up/down, `0x34`/`0x35` = the wheel tilt, whose factory value is mouse 4/5 — the `mouse_4`/`mouse_5` controls). Razer stores its profile with a mouse button as a firmware Hypershift key (category `0x0c`); the firmware then swallows that button (the software Hypershift trigger dies) and emits Synapse's layer-1 shortcuts itself — so any native button that is not its plain mouse button is drift. A mode read as non-`Normal` is only reported when `ensure_normal_mode`'s own re-read still says so (a `Normal` there was a transition). Timing: a check at once on start, `POLL_INTERVAL` normally, `FAST_POLL` while the mouse cannot be opened, the runtime is not running yet, or Razer's engine (`RazerAppEngine.exe`/`RzEngineMon.exe`) runs, `POLL_INTERVAL` while it does not answer (status `0x04`, `Verdict::Asleep` — nothing can change it meanwhile), and immediately on `request_check`. A tick reads only the mode (`Verdict::ModeOnly`); the full scan (every record + battery, ~23 commands) runs on start, on request, while Razer runs, after any verdict but a clean one (a wake-up included) and every `FULL_SCAN_EVERY` (5 min) — only Razer rewrites the records. A Razer engine start is reported as `razerStarted`. A clean verdict goes into the runtime log once per change; a throttled notification is still logged (at `info`).
- HyperShift 2 layers (`Layer::Hypershift2`, `Layer::HypershiftBoth`): the trigger is per profile (`Profile.hypershift2Triggers`, mechanism in `src/capture_backend/`); `resolver::HeldLayers::layer` picks the layer of the held triggers; per gesture HyperShift falls back to the standard binding, the HyperShift 2 layers do not (an empty button there does nothing, owner's call 2026-11-11). The live map counts a binding on the HyperShift 2 layer as needing the control's standard signal (`live_overlay::has_action`). The offline profile and banks never get these layers (the firmware has two).
- Software Hypershift: `Settings.hypershiftTrigger` names the native mouse button held as the modifier (default the right button). The device never emits the layer-1 record, so `resolver::resolve_input_preview_with_overrides` imposes the layer from the trigger state and falls back to the control's standard binding when the hypershift layer has no binding for it. The wheel needs the same treatment from the capture side: the firmware never encodes a scroll tick, so an encoder mapping tagged as a wheel direction is emitted by the mouse hook itself while the trigger is held. Mechanism lives in `src/capture_backend/`.
- Mouse settings (`get_native_model`, `get_mouse_settings`, `set_mouse_dpi`, `set_mouse_poll_rate`): `get_native_model` returns the connected model (else the config's) — name, DPI range, poll rates, `verified`, `connected` — from the catalog plus a registry lookup and an open handle, no vendor command; read/written live through the vendor command class — battery `0x07/0x80` (0..=255, reply byte 9), DPI `0x04/0x85`/`0x05` with a storage selector — `NOSTORE 0x00` the live value, `VARSTORE 0x01` also kept across power cycles (measured: a live write leaves the stored DPI; `dpi()` reads the live one) — a DPI write is skipped when that storage already holds it on both axes (the exit stores the offline DPI every time), poll rate `0x00/0x85`/`0x05` (`0x01` 1000, `0x02` 500, `0x08` 125 Hz). Every write is confirmed by reading it back. Per profile and mouse: `Profile.deviceMouse[deviceId]` (`mouseDpi` / `mousePollRateHz` / `mouseDpiStages`, all optional; pre-v5 flat fields are moved there for every built-in mouse on load, `migrate_mouse_settings`) are written into each connected mouse on every switch to that profile (`mouse_speed::apply_profile_mouse_settings`, own thread, called from `emit_profile_resolved_and_notify`) — the DPI live only (a switch per alt-tab must not wear the mouse's storage), and a switch superseded by a newer one (`PROFILE_SWITCHES`) is skipped; a profile without them leaves the mouse as it is. The Mouse tab's own DPI write (`set_mouse_dpi`) and the exit (`write_offline_profile`, the offline profile's DPI) store it. The first time a switch or a DPI step changes a mouse's live DPI / poll rate, the value it replaced is kept (`mouse_speed::Originals`, per device id, this run only — a restore process after a crash has none; a Mouse tab write forgets the field it set); the exit (`mouse_offline::restore_live_speed`) sets the offline profile's own poll rate and live DPI, else those originals — a V3 only its poll rate when a bank reselect follows (it sets the DPI). An unverified mouse gets no offline write and so no restore. A switch to a profile without mouse settings still supersedes an older queued switch, and a switch thread does nothing once the exit began. On every full scan the guard reads the battery of every present model, not only the one it guards (`poll_batteries`; a sleeping mouse keeps its last reading, an unplugged one drops out; a mouse whose read got no answer is asked again every tick and its first answer emits `mouse_battery` even when the level is unchanged, so the device cards stop saying "not answering" within one tick): `last_batteries` gives the tray tooltip one line `V3 Pro 100% · V2 9%` (`NativeModel.short_name`: Windows cuts the tooltip at 64 characters), `last_battery_percent` the corner badge — the mouse used last (`note_device_used`: any move or click of a catalog mouse, seen through raw input on the `system_events` window — `RIDEV_INPUTSINK`, device path → `device_catalog::model_for_path`, looked up only when the reporting device changes — or a button the capture dispatched, by the control's config device), else the lowest — drawn by `tray_badge.rs` with `Settings.showBatteryInTray`, and each change emits `mouse_battery` `{ model, percent, low }`; `low` is set below 10 % at most once per 24 h per mouse, remembered across restarts in `mouse-battery-warned-<device id>` (unix seconds) next to the config, with an OSD bubble naming the model.
- DPI stage actions (`MouseActionKind::DpiUp` / `DpiDown`) use the resolved profile, read actual live DPI, and choose the next higher/lower configured speed without wrapping or changing saved startup DPI. Writes are live-only (`set_dpi(..., false)`), serialized by the existing device lock and read-back verified. Missing stages and HID failures are explicit localized errors; live picker tests pass the profile ID and run blocking HID work off the async runtime.
- Mouse snapshot (`get_mouse_settings`): reads DPI, poll and battery independently under the existing device lock. Missing values serialize as null, never defaults. Device-open failure returns a snapshot; only exact `NOT_CONNECTED` is disconnected, all other failures are unavailable. Setters preserve their own read-back verification and return partial snapshots after success; failed confirmation remains an explicit error with no automatic retry.
- Device report (`get_device_report`, `open_device_report_issue`): `VendorDevice::probe_report` is read-only on any model, verified or not — Windows version, identity (VID:PID, interface), firmware (`0x00/0x81`), mode, DPI, raw poll code, battery (never the serial number — the report is public), then the raw 10-byte `0x02/0x8c` record of every button id that answers on layer 0, plus its layer-1 record (~20 s, holds `DEVICE_LOCK`). The Mouse tab's "Help verify" button (unverified + connected models) copies it and opens the `device_report.yml` issue form (`.github/ISSUE_TEMPLATE/`, label `device-report`); the report travels through the clipboard, never the URL. This is how a model gets its button table and moves to `verified` (plan `plans/multi-device/plan.md` §3.6 step 5-6).
- `get_device_report(detail)` accepts `summary` or `full`; absent detail preserves the full scan. Summary reads the common header only and returns application/Windows metadata even when open fails. It never scans button records, copies to clipboard or opens GitHub. Both modes omit serial/HID paths and all profile data.
- Offline profile (`mouse_offline.rs`): **one planner for every model**, `mouse_offline::plan(config, model, profile)` → `OfflineRecord`s; the onboard path writes them into profile 1, `live_overlay::write_offline` into the V3's banks. Models differ only by catalog data: `NativeModel.plain_left_modifiers` (the V3: plain records with the standard HID mask, never the turbo record; the V2: Shift/Alt shortcuts as the turbo `KeyTap`, a modifier-only hold with the right-hand bits) and the transport (the inert signal is Sidearm's own signal on the onboard path, a reserved `live_overlay::USAGES` consumer usage in a bank; an unbound control's layer 1 gets the inert signal in Sidearm's own profile 1, a bank keeps its record). Only a key with modifiers or bare modifiers (HID usage from `hid_usage_for_vk`, usage 0 = modifiers held alone) or a plain mouse button (wheel up/down included: records 9/10, the wheel's factory value) bound as a plain press can live in a record; text, macros, launches, menus, per-app profiles and a binding with a `DoublePress`/`TriplePress`/`Chord` `trigger_mode` (the firmware fires on every press; `Hold` is what a key record does) get the inert signal, never the old record. Layer 1 follows the resolver: the hypershift binding, else the standard one; a left click under a right-button settings trigger is a right click. The trigger (`LiveSpec.firmware_trigger`, else the settings trigger among the native buttons) gets `OnboardAction::Hypershift` (category `0x0c`) only when the profile has a playable hypershift binding; the profile button is never written. The profile is `offline_profile_id(config, in_effect)`. Markers are written atomically (`mouse_offline::write_marker`, a failure logged). The marker (`mouse-offline-written`) is only left by a write the mouse took at least one record of; a mouse that did not answer anywhere in the write (a record, its DPI, a bank reselect — `is_no_response`) is listed in `mouse-offline-failed` and the whole profile is retried; any other refusal is only logged (retrying it every 2 s would wear the storage), and `write_record` skips a record that already reads back as wanted. The next start turns a left `mouse-offline-failed` into the `offlineNotStored` notice; no mouse at all leaves neither. The exit stores the offline profile's own DPI (a profile without one leaves the stored DPI alone). Wheel tilt has no onboard record (all ids 0x00..0xff scanned on both layers, 2026-10-17): the firmware plays tilt itself on layer 0, so tilt under firmware Hypershift (horizontal scroll) is lost without Sidearm — a known limit, not a bug.
- Vendor HID exchanges are serialized process-wide: a `VendorDevice` holds `DEVICE_LOCK` for its whole life, because a reply is fetched by a separate `GET_REPORT` and two concurrent users (guard tick + an IPC restore) read each other's replies — measured as a bogus "mode 0x01" and a false "rewritten" report. Open it, do the work, drop it; never hold one while opening another.
- Vendor HID (`mouse_memory.rs`): the collection is opened with **no** requested access rights and a sharing mode (Razer's driver holds it — GENERIC rights fail `ERROR_ACCESS_DENIED`), the feature buffer is 91 bytes for report id `0x03`, `VendorDevice::open_connected()` opens the first `CATALOG` model found and the device then takes its transaction byte, slots, native buttons, DPI range and poll codes from that model (config-side helpers still assume `NAGA_V2_HYPERSPEED` until the config names its model), and a write is only trusted when the mouse echoes it (`SET` → two `GET` → retry). The registry keeps leaves of devices no longer present (another USB port, a re-paired dongle): `open_first` tries every matching leaf (the consumer reader uses it too). A command reply counts only when it echoes the request's class and command (`reply_matches`; Razer's driver shares the report from another process) — otherwise the command is resent; status `0x04` (`NO_RESPONSE`, `is_no_response`) is a mouse that did not answer. The **slot** query cannot cold-read: a `GET_REPORT` answers only with what the previous `SET_REPORT` stored, so `verify_onboard_mapping` confirms an assignment by writing it. The **command** class does answer honestly and is what the guard reads: `class 0x00 / cmd 0x84` returns the device mode (`0x00` Normal = the firmware emits the onboard records; `0x03` Driver = Razer's driver maps the buttons instead) and `class 0x02 / cmd 0x8c` with `[profile=1, button, layer=0, …]` returns the stored record at reply bytes 11..=14 (`category, modifier, usage`; a mouse-category `0x01` record carries the button number where a key record has its modifier). Its twin `class 0x02 / cmd 0x0c` with `[profile=1, button, layer=0, category, len, value…]` writes a record (`restore_native_button`, and key records for the slot-less top buttons `0x0b`/`0x0c`) — the slot path's "marker" `0a 02 0c 01` is this same header. On the V2 HyperSpeed key records carry a HID modifier mask, written as Ctrl `0x01`, Win `0x08`, **right** Shift `0x20`, **right** Alt `0x40` (`modifier_bits`): that firmware never plays the left Shift `0x02` or left Alt `0x04` bit, alone or combined — measured 2026-10-27 at the Raw Input level, every other bit arrives. Limit: on a layout with AltGr (Russian) Windows adds Ctrl to the right Alt, so a stored `Alt+X` plays as `Ctrl+Alt+X` there. Records Synapse stored with `0x02`/`0x04` only ever played through Razer's driver mode, never from onboard memory. The **turbo** key record (category `0x0d`, `[0d, 04, modifier, usage, period_hi, period_lo]`) does play the left Shift and Alt with the standard mask (measured, Raw Input): the V2's offline profile writes a shortcut with Shift or Alt as `OnboardAction::KeyTap` — a turbo record with `KEY_TAP_PERIOD_MS` (10 s), i.e. one tap per press (`0xffff` played nothing) — so Alt+F4 works in any layout. A turbo record cannot hold: a modifier-only hold keeps the plain record with right-hand Shift/Alt. thumbs are bare `F13`..`F24`, the top buttons `Alt+F23`/`Alt+F24`; only `F13`..`F24` targets are ever written. **Signal kind** (`binding_target`): by default a key button of a model with `consumer` holds a consumer record instead — category `0x0a`, `[0a, 02, usage_hi, usage_lo]`, written on layers 0 **and** 1 with `0x02/0x0c` (no slot path) — and its press reaches the capture helper as a HID report, never as a key (`capture_backend/consumer.rs`). A file `onboard-key-signals` next to the config (`KEY_SIGNALS_FILE`, read at startup into `set_consumer_signals`) selects `F13`..`F24` instead; the Mouse tab switches it live (`set_key_signals` creates/removes the file, flips the flag, marks the switch as the user's own — `USER_SWITCHED_SIGNALS`, so the guard's rewrite raises no `signalsSwitched` notice — rewrites the mouse itself — a mouse that cannot take it now is left to the guard — and restarts capture when the runtime is running so the helper follows; it returns when all that is done, and a stopped runtime stays stopped). `get_native_model` reports the mode as `consumerSignals` (`null` for a model without the consumer path). The guard treats a button holding Sidearm's signal of the other kind (`holds_other_signal`) as a quiet signal switch, not a takeover, and the onboard path's offline inert fallback is the same signal (`binding_target`). Proven on hardware (`cargo test -- --ignored`). The record payload bytes 9..14 are `button_id, layer, 0x02, len, modifier, hid_usage`; `layer` is `0x00` on the slot path (`0x01` plays only under the firmware Hypershift and is written through `write_record`) and `modifier` is the HID mask above (`0x00` for a plain `F13`..`F24`).

- Connected mice: `mouse_memory::present_models()` lists the catalog models whose vendor interface Windows reports present (`CM_Get_Device_Interface_ListW`, no device traffic). `VendorDevice::open_onboard()` opens the connected onboard-path mouse (guard, offline profile, onboard IPC), `open_for_device(device_id)` the mouse of a config device (Mouse tab IPC: `get_native_model`, `get_mouse_settings`, `set_mouse_dpi`, `set_mouse_poll_rate`, `get_device_report` take an optional `deviceId`), `open_model(model)` one model, `open_connected()` any. `list_native_mice` returns the connected models' `NativeModelInfo` (with `deviceId`, `banks`). Each catalog model has its own device lock (`DEVICE_LOCKS`): one receiver is one exchange at a time, two receivers work in parallel.
- `src/system_events.rs`: a hidden top-level window for two broadcasts Tauri does not pass on, and for mouse and keyboard raw input (which catalog mouse is in use, for the tray battery badge, and which of its keys/buttons are held, `live_overlay::note_input`). `WM_DEVICECHANGE` (debounced, compared by connected model) emits `native_mice_changed` and restarts capture, so the live maps follow the mice actually plugged in; the frontend reloads the config when a new mouse's device is missing (loading seeds it). `WM_ENDSESSION` (shutdown, restart, logoff) runs `shutdown_mouse` — the same once-per-process exit as `RunEvent::Exit` (the second caller waits for the first, so the process never ends mid-write; it sets `is_shutting_down`, then `onboard_guard::wait_tick` waits up to 5 s for a guard tick that began before it — the tick holds `TICK` from its shutdown check on — so no tick puts signals over the offline profile): stop capture (restores every live map: `live_overlay::stop_sessions` restores them on a thread of their own, and `shutdown_mouse` then waits up to 30 s for every session — a reload's included — with `wait_idle`, so a mouse stuck in a HID call cannot hang the exit; a config reload hands its stale sessions to the same thread, and a new session's worker waits — as long as it takes, without blocking whoever started it — for the previous session of that mouse to end before it claims `ACTIVE` and writes (a session stopped while still waiting never clears its predecessor's flag) — two never share a mouse's rollback file or `ACTIVE` flag), then store the offline profile. A Sidearm killed or crashed never restores and stores no offline profile: the V3 then plays Sidearm's silent signals, wheel included, until its profile button reloads a bank, and the V2's thumbs keep Sidearm's signals. So every Sidearm starts a **watchdog** at setup (`mouse_restore::spawn_watchdog`): `Sidearm.exe --spawn-watchdog <config dir> --watch <pid>` relaunches itself as `--restore-live-maps <config dir> --watch <pid>` and ends, so the watchdog's parent is gone and Task Manager's "End task" (which takes Sidearm and its capture helper together — measured 2026-11-10 on the notebook's V2: no restorer ran and the thumbs stayed silent) leaves it running. It waits for that pid to end; a clean exit's last step writes `sidearm-clean-exit` with its pid (`mark_clean_exit`), and then the watchdog quits, otherwise it continues as the after-crash restore below (logged in `restore.log`). As a second line, a capture helper (same exe, `--capture-helper`, given the config dir in its init line) whose stdin closes without the `EXIT` line a stop writes first starts a detached, hook-free `Sidearm.exe --restore-live-maps <config dir> --after-crash` (`mouse_restore::restore_live_maps_main`) and exits at once; `--after-crash` makes it queue the offline profile (`offline_profile_id(config, None)`: the fallback for `@active`) in `mouse-offline-failed` when no exit did, so it is stored like an exit would. It logs to `restore.log` in Sidearm's log folder (env_logger; there is no Tauri log plugin in it). That process waits up to 15 s for `Local\Sidearm-app` (held by every running app from `run()` — `claim_app` keeps a handle even when an exiting Sidearm still holds it, measured 2026-11-11: a Sidearm started during an exit that waited on a sleeping V2 ran without it, and the restorer kept both mice for good) to disappear (still there = Sidearm is alive, quit — before taking any mutex, so a live Sidearm is never paused), takes `Local\Sidearm-live-map-restore` (one restorer at a time), then retries `live_overlay::restore_orphaned` — and, while `mouse-offline-failed` names a profile (first line) and the mice that slept (one device id per line), `mouse_offline::retry_offline_profile` — only those mice, so one that took the profile is not rewritten every retry; a pending mouse switched off keeps waiting — (an exit whose mouse slept spawns the same process) — every 2 s while a mouse sleeps (every minute after 30 min), until the work is done or a Sidearm starts — never giving up, so a mouse that sleeps for hours is not left silent; while it waits, an HKCU `RunOnce` value (`SidearmRestoreMice`) brings it back at the next logon, removed when it ends. While the restore mutex exists a starting Sidearm leaves the mice alone (`live_map_restore_running`: live sessions wait, the guard counts as not running), so two processes never talk to one receiver. Both mutexes get an explicit DACL (authenticated users, `create_mutex`): with the default one an elevated Sidearm's mutex is invisible to a non-elevated process; `mutex_exists` also counts an access-denied mutex as present, so no check fails open.
- `src/live_overlay.rs` (module `mouse_memory::live_overlay`): reversible live `profile=0x00` maps for every model with a `LiveSpec`. `live_models(present)`: a `LiveOverlay` model always, an onboard model with a live path only while another native mouse is connected (one software trigger cannot tell two mice apart, so each mouse's firmware holds its own HyperShift). `software_hypershift(present, live)`: the mouse hook's trigger is on while an onboard-path mouse is connected or none is. `overlay()` builds one model's targets and consumer signals: key buttons always, extra and native controls only for an enabled non-disabled action (or the setup check), the settings trigger (or the model's firmware button) as `Hypershift` on both layers, left click → right click under a right-button trigger, `F13`..`F24` key records in keyboard-fallback mode (a key button without one is an error). `configure(config, present)` adds the config device of a connected verified `LiveOverlay` model once, with its controls and one reserved alias per control and layer and no bindings (copying assignments is the frontend's `device-transfer.ts`). A `Session` per model writes the map, keeps a rollback file (`<device_id>-live.json`, matched to the receiver by VID/PID so another USB port still restores; the 2026-11-08 rc names are migrated), checks one record every two seconds (two mismatching reads = drift), repairs only differing records (a record read as the same foreign value twice is adopted as the new original, a single odd read is not), never writes a live record while a button of that mouse is held (`write_bank` → `wait_released`, at most 5 s: `HELD` per model, fed by the capture helper's reader lines and by raw keyboard/mouse input from the mouse's own collections in `system_events` — rewriting a record under a held button strands the old record's key, measured as a stuck Shift+Enter), restores on stop (a record read as something else twice is the user's change and stays; a single odd read does not drop it) and reports `is_active`/`is_ready`; a snapshot that would take Sidearm's own signal (reserved consumer usage, `F13`..`F24`) as the original takes a native button's plain record instead, or keeps it with a warning; HID presses of an active model are dispatched only once it is ready (`events_allowed`). An onboard model's session first restores an offline profile the last exit left (marker). A failed rollback is logged and the original write error returned. `live_map_ready(deviceId)` tells the setup wizard whether a mouse's buttons reach Sidearm (a live map verified, or an onboard mouse connected).
- Onboard banks (`LiveSpec.banks`, the V3's stored profiles, class `0x05`: count `0x80`, inventory `0x81`, active `0x84`, select `0x04`; `parse_banks` checks they agree). `Profile.device_slots` (`deviceSlots`, device id → bank 1–5) links a profile to a bank; `get_onboard_banks(deviceId)` returns the assigned banks and the active one. Banks are written only at exit (`write_offline`): every linked profile into its bank, or — with one bank and no link — the offline profile; an unlinked bank that Sidearm wrote earlier (a rollback file exists) gets its own records back, others are left alone. Each written bank has a rollback file (`<device_id>-bank-<n>.json`) and read-back verification, and gets the profile's own DPI for that mouse (the V3 keeps a DPI per bank and switches to it with the bank; `set_dpi_in(bank, …)`, storage byte = bank, measured readable with `0x04/0x85`); afterwards the offline profile's bank (else the one that was playing) is selected, which reloads the live map from it. Sidearm never switches banks while it runs: the firmware would replace the live map. When the user does (the profile button), the session watches the active bank every tick and repairs the live map at once. A bank never gets the turbo key record (`NAGA_V3_PRO.plain_left_modifiers`: a plain key record with the standard HID mask, the form Synapse stores — Alt+F4 = `02 02 04 3d`; a turbo record repeats while the firmware thinks the button is held, and the V3 fired a stored Alt+F4 turbo every 10 s on its own, Sidearm closed, measured 2026-11-10). Measured 2026-11-10 with `live_overlay::tests::v3_plain_left_modifiers` (interactive): the V3 plays a plain record's left Shift `0x02`, left Alt `0x04` and right Shift `0x20` as such, and right Alt `0x40` as AltGr (LCtrl+RAlt) on the Russian layout — so a right-hand Alt is wrong for the V3. The V2 HyperSpeed drops the left bits, so its onboard path keeps the turbo tap. What a bank gets comes from the shared planner (`mouse_offline::plan`, see Offline profile). A failed live-overlay offline store from a sleeping mouse leaves `mouse-offline-failed` like the onboard path.
