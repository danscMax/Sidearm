# src-tauri — Backend (Rust + Tauri v2)

## Purpose

The Rust backend: low-level keyboard capture, Razer-encoding detection, action execution (keystrokes, mouse, text/snippets, sequences, launches), config persistence with backups/recovery, Synapse import, the mouse's own onboard button memory, window/foreground resolution, and the Tauri IPC surface.

## Ownership

- `src/lib.rs` — Tauri app setup + the `#[tauri::command]` handlers (the IPC surface called from `src/lib/backend.ts`).
- `src/config.rs` — `AppConfig`, load/save, schema + semantic validation (`validate_config`, also used by Synapse import IPC), atomic writes, rolling/daily backups, corrupt-recovery + newer-schema guard.
- `src/executor.rs` — runs actions; `src/input_synthesis.rs` — `SendInput` keystroke/mouse/text, clipboard paste, snippet-token expansion.
- `src/backup.rs`, `src/resolver.rs`, `src/window_capture.rs`, `src/hotkeys.rs`, `src/vk.rs`, `src/chord.rs`, `src/recorder.rs`.
- `src/device_catalog.rs` — one `NativeModel` descriptor per natively driven mouse (VID/PIDs, transaction byte, key-button ids, native buttons, DPI range, poll codes); `CATALOG` lists them: `NAGA_V2_HYPERSPEED` and `NAGA_V3_PRO` (verified) and `NAGA_V2_PRO`, `NAGA_PRO`, `NAGA_X` (unverified, data from openrazer + Synapse's button table; test `only_the_hardware_tested_models_are_verified` pins the list). Each model names its config `device_id` (`razer-naga` for the V2 family, `razer-naga-v3`) and `control_prefix` (`v3_`), its `Transport` (`Onboard`: persistent records in onboard profile 1 kept by the guard; `LiveOverlay`: only the reversible live map) and an optional `LiveSpec` (extra controls, firmware HyperShift button, onboard banks, display-name keys) that drives `live_overlay`. Nothing else branches on a model: add a model by adding its entry. Each model names its vendor USB `interface`: the registry leaf must contain `VID_…&PID_…&MI_<interface>` (`interface_needle`/`interface_path`; `3` on the Naga X). Model-specific values live here, never as constants in `mouse_memory.rs`. `consumer: Some(ConsumerSignals)` (V2 HyperSpeed per key button, test `consumer_usages_cover_every_key_button_once`; a live-overlay model takes its usages per control and layer from `live_overlay::USAGES`) gives each key button a reserved consumer usage and names the collection that carries the reports (`MI_01&Col03`, report id `0x02`). `verified: false` (a model not yet proven on hardware), or a `LiveOverlay` transport, makes `VendorDevice::require_verified` refuse every onboard-profile write that changes a button — `write_button`, `write_record`, `restore_native_button`, `ensure_normal_mode` — so such a model is only read and gets DPI/poll writes; the guard only reports its battery (`Verdict::ReadOnly`) and no offline profile is written or restored for it. Windows-only. Adding and verifying a model: `docs/ADDING-A-MODEL.md`; roadmap: `plans/multi-device/plan.md` (local).
- `src/mouse_settings.rs` — independent nullable live readings, per-field keyed warnings, complete/partial/unavailable/disconnected status, public error redaction and summary/full report formatting. A failed secondary reading cannot turn a confirmed setter into failure; open failure and no device are distinct.
- `src/mouse_memory.rs` — the mouse's vendor HID collection: opens it, reads and writes per-button records (`read_block`/`set_block`, `write_record` with read-back), reads the device mode and puts it back to `Normal` (`restore_onboard_control`, the takeover notice's and the setup wizard's "prepare mouse"). Sidearm's signals are never written into an onboard profile: they live in the live maps (`live_overlay`). Windows-only (`#[cfg(target_os = "windows")]` on the module).
- `src/mouse_offline.rs` — the offline profile, the chosen profile (`Settings.offline_profile_id`: absent = the fallback profile, `OFFLINE_PROFILE_ACTIVE` "@active" = the one in effect at the exit — which follows the focused window, so it is not the default) the mice play on their own so its single-key and mouse-button bindings work without Sidearm (layer 1 + firmware Hypershift on the trigger when the profile has playable hypershift bindings). An onboard mouse (the V2) keeps it in profile 1 for good (`store_onboard_offline`, run by its live session while Sidearm runs — `@active` is the fallback there — never at an exit); a bank mouse (the V3) gets it in its banks in the background and at the exit (`shutdown_mouse`, from `request_exit`'s worker — `RunEvent::Exit` as the fallback — or the end of the Windows session). Windows-only.
- `src/mouse_restore.rs` — the restore process a dead Sidearm leaves (`--restore-live-maps`), the named mutexes (`Local\Sidearm-app`, `Local\Sidearm-live-map-restore`, `claim_app`) and the elevated relaunch wait. Windows-only.
- `src/mouse_speed.rs` — each profile's DPI / poll rate written live on a switch, DPI Up/Down stepping, and the speed a switch replaced (`Originals`) for the exit to put back. Windows-only.
- `src/onboard_guard.rs` — the takeover watchdog: while the runtime is active it polls the onboard mouse's device mode, puts it back to `Normal` when Razer's engine took it (driver mode silences the live map too), reports it as `onboard_takeover` (throttled per kind, `NOTIFY_COOLDOWN`), reads every mouse's battery and reports a Razer engine start. It writes no button record: the onboard mouse's profile 1 holds the offline profile and its live map is the live session's. Windows-only.
- `src/synapse_control.rs` — explicit Razer application ownership transfer, validated process paths, and reversible per-user Synapse startup changes. Never touches services/drivers. Startup backups are bound to the Windows computer and logon user returned by Win32; only the exact HKCU Run/RazerAppEngine entry is supported, with original type/bytes preserved and read-back checked. Unknown startup mechanisms require Windows Startup apps. Process-list failure is unknown, not absence. The IPC recovery checks the runtime and verified mouse before closing Razer, restores/read-checks onboard settings through the shared restore helper, restarts capture, then optionally changes startup; partial startup failure is returned separately. Physical input still requires the user's test.
- `src/mouse_status.rs` — what the user must know about the mouse path that is not a takeover, emitted as `mouse_status` `{kind, active}` and kept for a window that opens later (`get_mouse_status` → `snapshot`): **states** held until cleared (`helperLost` — the capture helper died and was not restarted; `buttonsUnreadable` — the consumer reader cannot open its collection; `mouseUnreachable` — the guard failed for `UNREACHABLE_AFTER`, an asleep or absent mouse excluded — `Verdict::Asleep`/`Absent`, `mouse_memory::NOT_CONNECTED`; both states are cleared while the runtime is stopped; `watchdogOff` — `spawn_watchdog` found no watchdog mutex after two tries, or the watchdog had to stay in Sidearm's job (an elevated Sidearm in a job that forbids breakaway gets no `spawn_under_shell`), so a kill leaves the mice unrestored this run — shown in the Mouse tab and once as a toast) `mouseOffline` — the profile button took a mouse off Sidearm's own bank (`live_overlay::offline_models`; `lib.rs` `mouse_offline_mode_changed` also puts "⚠ {model} offline — back to Sidearm" first in the tray menu and a line in its tooltip, and shows one OSD bubble; the tray item, the window's toast button and `back_to_sidearm_bank` select Sidearm's bank again)) and one-time **notices** taken by the first snapshot (`noFreeBankSlot` — every bank slot holds a profile, so Sidearm writes the live map; `offlineNotStored` — the last exit left `mouse-offline-failed`). Windows-only.
- `src/webview2.rs` — the WebView2 footprint (Windows-only). `clear_caches` empties the profile's pure caches (`Default\Cache`, `Default\Code Cache`, `GrShaderCache`, `Crashpad\reports` — not `component_crx_cache`, whose downloads would come back every start — under `<user data>\EBWebView`: WebView2 nests its profile one `EBWebView` deeper than `WEBVIEW2_USER_DATA_FOLDER`) in `run()` after `claim_app` and before any webview, skipped while another process holds the profile's `lockfile`; never `Local Storage`/`IndexedDB`. No browser flags (`additional_browser_args`: not for production, per Microsoft). `low_memory_while_hidden` subclasses the main window: hidden or minimized sets its webview's `MemoryUsageTargetLevel` to `LOW`, shown/restored to `NORMAL` (never `TrySuspend`); the popups are left at `NORMAL` (their open latency is unmeasured). Measure with `tools/measure-footprint.ps1`.
- Manifests: `Cargo.toml`, `tauri.conf.json`, `capabilities/` (under src-tauri). The config JSON schema is `schemas/config.v5.schema.json` at the repo ROOT, bundled into `config.rs` via `include_str!("../schemas/...")`.
- A profile chosen by hand (tray, `profileSwitch`) holds until changed; while one does, the tray offers "Back to the app rules": now, or in 10/30/60 minutes (`schedule_rules_back`, the latest choice wins and a profile chosen meanwhile is kept), then `release_manual_profile` resolves the window in front by the rules at once.
- `src/menu_popup.rs` — the live popup of a `menu` action: `Model` (pure, unit-tested: the top level shows its submenus as **blocks** — a heading over their items, inline, numbers running on through all blocks — a submenu inside a block opens as its own level; a search shows every enabled action of the tree whose name or sent text matches; highlight, back) and the `menu` window (`public/menu.html` + `menu.js`, created on first open, transparent around the list and the tip, capability `capabilities/menu.json`). The popup takes the keyboard focus (`set_focus`) so typing searches, arrows/Enter pick and Esc closes without reaching the app; picking or closing from the menu gives the focus back to the window it opened over (`restore_foreground`) before the item runs; a click elsewhere or another window in front just closes it (watcher thread; also after 60 s). The page draws the `View` Rust emits (`menu-show`, with `placeholder`/`empty` from `backend.menu.*`), measures itself (`menu_layout`, in physical pixels at its own `devicePixelRatio`, again on a resize or scale change — a fresh window still on another monitor was cut off when Rust multiplied CSS pixels by the target's scale) and forwards input (`menu_hover` only on real pointer movement, `menu_pick`, `menu_back`, `menu_wheel`, `menu_search`, `menu_confirm`, `menu_close`); Rust sizes it and places it at the cursor: the first layout of a menu pins the list (`display::position_near` for the list alone) and the tip's side (`Placement`: right of the list while 3 columns fit there (`RIGHT_TIP_COLUMNS`, owner's call), else on the side with more room); later layouts only resize around them, so a tip widening never moves the list. `menu_layout` answers the placement; the page draws the tip on that side (`menu--side-left`) and caps its columns to the room (`sideRoom`), and a still-hidden menu whose tip is on the other side waits for the page to measure again. Pinned action items (`MenuItem.pinned`) come first in a ★ block and only there. A search also looks through every other menu (`Model::with_others`, grouped under the menu's name, links to menus skipped, an action found once); within each group a name starting with the query comes first, then a name holding it, then a text match (`Model::rank`, stable — no frequency, so a query always gives one order and thumb N picks the same item); the search box's scope switch (and Tab) limits it to this menu (`menu_search_scope`, `Model::set_scope`), and the page marks the matched part of each name. After 600 ms on a phrase the tip asks `menu_full_text { index }` for its whole text and widens, PageUp/PageDown scroll it. Each item carries `detail`, what it sends (`action_detail`), or for a submenu `children`, the rows of its level (one per line, pinned ones left out), shown in the tip beside the highlighted row so the list never changes shape under the pointer (a list taller than the menu splits into balanced columns, up to 5, the side widening and the window following, the list staying put — `splitIntoColumns` in `menu.js`; a linked menu's block stays whole in one column); a click on one of them takes it directly (`menu_pick_child { index, child }` → `Model::pick_child`). An action's optional `notes` is its description: `ViewItem.note` heads the row's tip (above what it sends), `childNotes` shows in a box under a tip name while the pointer is on it (`showNote` in `menu.js`), and the search matches it like the name (`action_notes`; a disabled placeholder's note is left out). The picked item runs through `capture_backend::run_menu_item` on the opening press's profile/control/layer; an item whose action is another menu shows as a submenu holding that menu's current items (`Model::expand_links` at open: its search box left out, its blocks as headings in the level and in the tip — `ViewItem.childGroups` —, an edit goes to that menu; the opening menu and any menu already on the way stay plain links that open it in place of this one, so no cycle), so one list can sit in many menus — `validate_config` rejects only an item opening its own menu; a link is never an inline block and its items are searched under the linked menu's name, not twice; a right click on a phrase offers `PickMode` Run / Enter (run, then Enter after 80 ms — only Run for an action that already ends with Enter, a phrase's `pressEnter` or a sequence whose last input is Enter, `pick_mode_for`) / Copy (its whole text into the clipboard, nothing typed; `menu_pick { index, mode }`) and, on a phrase or a list, Edit (`menu_edit { index }`: the menu closes, the main window comes up and gets `menu_edit_requested { menuActionId, itemId, profileId }` — the item's own menu, also for a search hit from another menu). The search also matches a query typed in the other keyboard layout (both sides compared as ЙЦУКЕН/QWERTY keys, `hotkeys::normalize_cyrillic_key`). Every action run is counted per day in `press-log-<computer>.json` next to the config (`src/press_log.rs`; one file per computer, added up when read — `src/machine_files.rs`, so a synced data folder never has two computers rewriting one file; places `profile|layer|control|gesture` and action ids, 90 days, written at most every 15 s and at exit, wheel scrolling left out, `get_press_log`; `export_layout_folder` copies it with the config, `menu-usage.json` and the device photos). Every pick is counted in `menu-usage-<computer>.json` next to the config (per computer, added up; an old `menu-usage.json` is still read) (`src/menu_usage.rs`, `get_menu_usage`; never in the config, so a pick does not rewrite or sync it). A radial look would be another drawing of the same `View` (its config field and schema bump come with it). Fake mode keeps the model and skips the window.
- `MenuItem::Separator { id }` is a line between items: never enabled (not highlighted, hovered or picked), no number — a side button picks the Nth item with lines skipped (`Input::Number`, `Model::row_of_number`; `Input::Pick` is a row index, a click), drawn as a line in the list and in a submenu's tip.
- `MenuItem::Search { id, enabled, allMenus }` is the popup's search box as an item: one per menu, top level only (`validate_config`; a menu of nothing but it counts as empty), never enabled, no number. Its place among the top-level items decides where `menu.js` draws the box (`View.searchPlace`: first → "top", fixed above the rows and the ★ block; last → "bottom", fixed below; between → "row", among the rows; a list or the results keep the top or the bottom); `enabled: false` hides the box and typing searches nothing (`Model::search_on`; a cheat sheet always searches), `allMenus: false` starts the search in this menu only (Tab still switches while open). `migrate_menu_search` gives a menu without one its box first (where it always was); the editor's draft does the same (`withSearchItem`).
- Delegated to children: `src/capture_backend/`, `src/synapse_import/`, `src/platform/`.

## Local Contracts

- `get_offline_preview(config, profileId, deviceId)` accepts the current draft (unsaved edits included) and returns camelCase `OfflinePreview { target, controls }`. Exit writers and preview consume the same `mouse_offline::plan`: each control/layer has preview metadata plus an optional record; `records()` extracts only writes. Never duplicate binding precedence, firmware roles, native fallbacks or layer availability in another planner. Controls distinguish own/inherited/preserved/silent/role/unavailable; role and unavailable entries are not editable.
- Preview bank targets use the exit writer's `live_overlay::bank_plan` with inventory read through `live_overlay::banks` on a blocking worker. Failed inventory (asleep/absent included) is `unknown`; `@active` without a fixed bank target is `followsWindow`. Bank management IPC (`create_onboard_bank`, `delete_onboard_bank`, `flush_onboard_banks`) wraps `live_overlay::{create_user_bank, delete_user_bank, flush_bank_store_now}` (enforcing max 5 slots, refusing deletion of Sidearm's slot or the last remaining user slot, switching away before deleting an active slot, and cancelling any pending 5 s background store before immediate verified write + hybrid reconcile). All bank commands are main-window-only in the handler, `APP_COMMANDS` and default capability.
- Preview targets expose `pending` for the onboard mouse's kept profile until this run stored that very profile in its profile 1 (`live_overlay::onboard_offline_stored`: a sleeping mouse, an unsaved draft), `writtenProfileId` for an unwritten no-bank profile and `banks` from the exit bank plan; silent/unavailable controls carry the planner's `reason` (`liveActionType` only for `actionType`), with absent optional fields omitted.
- Live setup reversibly restores saved pre-offline records for bank extras outside the live targets, without resolving offline bindings. Those raw targets join the live snapshot, drift repair and stop/crash rollback; stored bank contents stay unchanged. A confirmed bank switch ends ownership of the old live map before replanning from the new bank's snapshot. An own silent/unplayable offline override with no standard encoder mapping still gets a reserved consumer record; derived fallbacks keep their existing behavior.

- A path the page sends (import, export, folders, device photos, shortcuts) must be on a local drive (`is_local_path`, inside `validate_user_file_path`) before any file system call: touching `\\server\share` would offer that server the user's NTLM credentials.
- Internal fns return `Result<T, String>`; convert to `CommandError` at the IPC boundary. An error the UI shows is `CommandError::from_ui(code, ui_text!("error.*", …))` (a passed-through internal reason goes in as `{reason}` inside a translated frame; technical details via `.with_details`); `tests::untranslated_command_errors_do_not_grow` ratchets the remaining `CommandError::new` calls. A config declaring a newer schema is `ConfigStoreError::NewerVersion` → `config_newer_version`, never recovered or overwritten.
- Config load/save responses carry a non-serialized `stamp` of the exact bytes read/written; IPC adopts that snapshot's stamp without rereading the current file. Migration carries the saved stamp forward. The IPC acceptance step also applies minimize-to-tray and the trimmed/defaulted global shortcut on load, save, import and restore.
- Runtime lifecycle changes hold the controller lock through backend work, the corresponding `RuntimeStore` update and event emission; the store lock is released during backend stop/join. Start rechecks the running state under the controller lock. Tray toggles use the same IPC handlers.
- Press counters start one background flush timer on the first real count; pending counts are flushed every 15 seconds even without further input, on export and at exit. Empty ticks neither resolve paths nor write; failed reads/writes retain pending counts for retry.
- App command ACL: `build.rs` `APP_COMMANDS` lists every `generate_handler!` command (`AppManifest::commands`), so a command runs only in a window whose capability allows it (`allow-<command-with-dashes>`): `default.json` (main) all but the popups' own, `menu.json` only `menu_*`, `cheatsheet.json` only `cheatsheet_*`, `osd.json` only `osd_ready` (the page says it listens; a bubble asked for while it loads waits in `OSD_PENDING` and is shown then) and `osd_click` (a click hides the bubble; the "mouse offline" one, shown 10 s, also puts the mouse back on Sidearm's bank — `OSD_SAYS_OFFLINE`, cleared by any other bubble), `prompt.json` only `prompt_*`. A new command goes into the handler, `APP_COMMANDS` and one capability; `tests::app_acl_lists_every_command` fails otherwise (a command missing from `APP_COMMANDS` is rejected everywhere). `permissions/autogenerated/` is build output (ignored).
- **Text in Rust is English.** The file log (`log::*`, also the UI's log panel) and error strings (`Err(String)`, `CommandError::new`) are plain English. Text the UI shows to the user — runtime log entries (`record_*`, message is `ui_text::UiText`), `RuntimeErrorEvent.message`, execution `summary`/`warnings` — is built with `crate::ui_text!("area.name", "English with {name}", name = value)`: a key under `backend.` in `src/i18n/locales/{en,ru}.json` (`{{name}}` placeholders) plus the English fallback; the frontend renders it with `uiText()` (`src/lib/ui-text.ts`), and `normalizeCommandError` translates a keyed `CommandError::from_ui`. Log categories are English ids (`capture`, `execution`, `resolution`, `runtime`, `windowCapture`, `clipboard`, `textInput`; names in `log.category.*`). The tray and the OSD are drawn by Rust: the frontend sends the current language's `backend.*` texts (`set_native_texts`, at start and on every language change) and Rust uses `ui_text::native(&text)`, which falls back to English. The test `src/lib/ui-text.test.ts` fails when a `ui_text!` key is missing from either locale. Cyrillic stays only where it is data: the ЙЦУКЕН layout table, test fixtures, Synapse's `Макросы` folder, the seeded default snippets.
- Load migrations (`load_and_validate`, `read_and_migrate_config_file`; idempotent, kept by the next save): `migrate_devices`, `migrate_mouse_settings`, `migrate_paste_mode` (clipboardPaste → sendText) and `migrate_enter_phrases` — a macro of exactly [text without delay/repeat, 80 ms pause, `Enter`] (the pre-`pressEnter` phrase, `menu-phrase.ts` `phraseOf`) becomes an inline text with `pressEnter`, keeping id, name, notes and conditions; a text with braces but no token stays a macro (the two type it differently).
- Config is schema-first: the bundled `config.v5.schema.json` validates raw JSON before deserialize. A persisted field rename needs `anyOf`(both names) in the schema + `#[serde(alias)]`. Keep the Rust structs, `src/lib/config.ts`, and the schema in sync.
- `config.json` changed outside Sidearm (by hand, a script, a sync) is picked up without a restart: the `config-watch` thread (`spawn_config_watch`) checks its modification time every second, and a content stamp that differs from `ConfigStamp` (which every own save/load updates) and holds for one more poll emits `config_changed_externally` (the UI reloads) and restarts a running capture from disk.
- `read_text_folder` (menu editor "Add from folder"): the `.txt`/`.md` files directly in a user-chosen folder (≤ 1 MiB each, ≤ 200, UTF-8); their text is copied into the config, the folder is never referenced.
- `send_shortcut` sends its plan in three `SendInput` batches 30 ms apart (`MODIFIER_STEP_DELAY_MS`, `split_shortcut_plan`): the modifiers it presses, the key down+up, the modifiers up; `send_shortcut_hold_down` the same for modifiers then key. One batch fails two ways: Windows Terminal (Claude Code in it) reads the modifiers as up by the time it handles the key and types a bare "v"/"м" for Alt+V; the Remote Desktop client (mstsc) re-syncs a modifier that came in the same batch as the key and forwards it as up before the key (measured on both ends 2026-11-13: Alt down, Alt up, V on the remote).
- Hold shortcuts share synthetic modifiers and primary keys through `input_synthesis::HELD_KEY_OWNERS`; only the last owner sends key-up. Logical modifier owners survive text/emergency clearing; each new hold checks the live modifier snapshot and reasserts any released modifier. Physical modifiers are never claimed. Mouse actions retry their final modifier release once and report persistent cleanup failures, including the mouse error when both fail.
- A long phrase (over `CLIPBOARD_PASTE_THRESHOLD`, 100 characters) is pasted through the clipboard (`paste_via_clipboard`), tagged `CanIncludeInClipboardHistory`/`CanUploadToCloudClipboard` = 0 so it stays out of Win+V history and the cloud. With a remote desktop client in front (`mstsc.exe`, `msrdc.exe`, `vmconnect.exe`, `remote_desktop_in_front`) it leaves out `ExcludeClipboardContentFromMonitorProcessing` — the client's clipboard redirection is a clipboard monitor and skipped the staged text, so the remote session pasted its old clipboard (2026-11-20) — and puts the clipboard back after 1.5 s instead of 150 ms (the remote side fetches the text over the network when its app asks).
- Windows clipboard repair keeps reading, format inspection and replacement in one open session; paste snapshots and stages text plus a per-paste identity token in one session, then reopens to verify that identity before accepting the post-close sequence. Paste/selection restoration checks the sequence after acquiring the clipboard lock. Text modifier clearing releases the actual left/right sides and fails if Ctrl/Alt remain down after the bounded wait. Linux shortcuts and holds validate every step before their first emit, and error cleanup releases supported keys even when its plan contains an unsupported VK. Modifier-only Alt/Win holds use the menu mask key only on Windows.
- Config writes are atomic (temp + rename); backups (rolling rotation, daily snapshot, last-known-good) are best-effort and never fail the save. A corrupt `config.json` recovers from last-known-good/rolling backups; a config declaring a newer schema version is never overwritten.
- Config load/recovery and saves hold the persistent `config.lock` file's exclusive OS lock across validation, stamp checking, backups and commit. Responses carry an internal, non-serialized stamp captured under that lock; IPC adopts that stamp instead of re-reading a later writer's file. Cooperating processes serialize; external editors that ignore the lock can still race the commit. Read/metadata I/O errors never trigger corrupt recovery; invalid UTF-8 is a content error. Backups use atomic replacement; incomplete JSON daily snapshots are retried.
- `config::MAX_SEQUENCE_STEPS` (200) bounds saved sequences, macro recording and Synapse merge. `record_keystroke(key, text?)` (`text`: the character a printable key typed, `event.key`, sent without Ctrl/Alt/Win) returns how many steps the recording makes so far: keys with a `text` at most `TYPING_GAP_MS` (1 s) apart are one Text step with the typed characters (any layout; braces that would form a token or `{input:…}` are doubled), a lone one stays a Send, everything else is one Send each. A key that would start step 201 is ignored (and keys past `MAX_RECORDED_KEYS`), and Stop returns at most 200 steps. The frontend caps its counter and IPC submissions by that returned count, waits for pending submissions before Stop, and shows a limit warning; the backend cap alone does not notify the user. Oversized imported macros and their bindings are skipped with a localized warning, never truncated or counted as added.
- Profile resolution uses only enabled fallback profiles; an unavailable fallback leaves input unresolved (config validation keeps its disabled-fallback warning). Literal `titleIncludes` checks use Unicode lowercase; regex checks keep their existing normalization and compilation guards.
- Sequence Send/Text inputs share `executor::run_repeated_input`: repeat defaults to 1, zero skips input and delay, repeats cap at 100, and an optional delay follows every input. Live waits use `sequence_delay_ms` (30 s cap) and remain cancellable. The recorder attaches each gap to the preceding step and leaves the final step without a trailing delay.
- A Sidearm that starts while another one is exiting waits up to 60 s for it to be gone (`claim_app`: the exit creates `Local\Sidearm-exiting` first thing, `mouse_restore::mark_exiting`). Overlapping, both used one WebView2 data folder (`data\EBWebView`), whose environments share their processes: the new window sometimes never came up and no capture started (e2e scenario 9, red without the wait, measured 2026-11-11).
- "Run as administrator" (`relaunch_as_admin`) starts the elevated Sidearm with `--relaunched`; that process waits up to 60 s for `Local\Sidearm-app` to disappear before it starts (the old one restores its mice on exit, and the single-instance lock would turn the new one away).
- `src/admin_autostart.rs`: the elevated logon task never starts Sidearm.exe directly — it runs System32 PowerShell with a verifier script (in the task XML) that checks SHA-256 of the exe + every sibling `*.dll` pinned at enable time and holds them open until Sidearm is up. Re-running `enable()` re-pins (the "confirm after update" path, `needsReconfirm`; also raised for a task whose script differs from the current verifier). Keep `%` and `"` out of the script, and **no cmdlets** in it — only .NET calls: a cmdlet loads its module from `PSModulePath`, whose per-user folder is writable without admin rights (the test lists the forbidden prefixes). Registering/deleting needs admin: an elevated Sidearm does it in-process; a non-elevated one runs its own exe elevated with `--admin-autostart enable|disable` (`runas`, dispatched in `main.rs` before Tauri starts) and maps the helper's exit code (0 / HRESULT / 1) — never use the `Elevation:Administrator!new:` moniker, Task Scheduler is not registered for it (`CO_E_ELEVATION_DISABLED`). The task XML must stay within its declared schema 1.2 (an unknown element fails registration with 0x80041316).
- Self-injected input carries `INTERNAL_SENDINPUT_EXTRA_INFO`; VK 0xE8 is the mask/probe key (`vk.rs` `VK_MASK_KEY`), deliberately not a modifier. **Every `dwExtraInfo` tag must fit in 32 bits**: a `WH_MOUSE_LL` hook receives it truncated to its low dword (measured: `0x1122334455667788` arrives as `0x55667788`, while a `WH_KEYBOARD_LL` hook sees the full value). A wider tag stops matching in the mouse hook, which then treats our own injected clicks as physical presses and swallows them.
- Takeover guard (`onboard_guard.rs`): a takeover is only ever reported for a mode the guard **read** as non-`Normal`. A mode read-back is retried (`MODE_CONFIRM_ATTEMPTS`) because a `SET Normal` whose read-back still said `Driver` was `Normal` one second later (hardware measurement), so a transition must never be reported as a failed takeover; a mode read as non-`Normal` is only reported when `ensure_normal_mode`'s own re-read still says so. A refused command (an idle/sleeping wireless mouse answers status `0x04` to every vendor query) is not evidence of a takeover — log at debug and wait for the next tick. The guard is silent while `RuntimeStore::is_running()` is false: a stopped Sidearm does not fight Razer for the mouse. Timing: a check at once on start, `POLL_INTERVAL` normally, `FAST_POLL` while the mouse cannot be opened, the runtime is not running yet, or Razer's engine (`RazerAppEngine.exe`/`RzEngineMon.exe`) runs, `POLL_INTERVAL` while it does not answer (status `0x04`, `Verdict::Asleep` — nothing can change it meanwhile), and immediately on `request_check`. A tick reads the mode (`Verdict::ModeOnly`); the battery scan of every mouse runs on start, on request, while Razer runs, after any verdict but a quiet one (a wake-up included) and every `FULL_SCAN_EVERY` (5 min). A throttled notification is still logged (at `info`).
- HyperShift 2 layers (`Layer::Hypershift2`, `Layer::HypershiftBoth`): the trigger is per profile (`Profile.hypershift2Triggers`, mechanism in `src/capture_backend/`); `resolver::HeldLayers::layer` picks the layer of the held triggers; per gesture HyperShift falls back to the standard binding, the HyperShift 2 layers do not (an empty button there does nothing, owner's call 2026-11-11). The live map counts a binding on the HyperShift 2 layer as needing the control's standard signal (`live_overlay::has_action`). The offline profile and banks never get these layers (the firmware has two).
- Offline layers (`Layer::Offline`, `Layer::OfflineHypershift`): own per-profile/control assignments for firmware layers 0/1, never live bindings (`Layer::is_live`). Only a plain press (`None`/`Press`) of a `shortcut`, `mouseAction` or `disabled` action is valid; encoder mappings and cheat-sheet actions cannot target them. Explicit silent native-button assignments use reserved consumer usages; derived native-button fallbacks keep their native behaviour. Resolver, capture, live overlay and cheat sheets exclude offline bindings. Synapse `ReplaceByName` replaces live bindings and preserves own offline bindings and their referenced actions.
- Software Hypershift: `Settings.hypershiftTrigger` names the native mouse button held as the modifier (default the right button). The device never emits the layer-1 record, so `resolver::resolve_input_preview_with_overrides` imposes the layer from the trigger state and falls back to the control's standard binding when the hypershift layer has no binding for it. The wheel needs the same treatment from the capture side: the firmware never encodes a scroll tick, so an encoder mapping tagged as a wheel direction is emitted by the mouse hook itself while the trigger is held. Mechanism lives in `src/capture_backend/`.
- Mouse settings (`get_native_model`, `get_mouse_settings`, `set_mouse_dpi`, `set_mouse_poll_rate`): `get_native_model` returns the connected model (else the config's) — name, DPI range, poll rates, `verified`, `connected` — from the catalog plus a registry lookup and an open handle, no vendor command; read/written live through the vendor command class — battery `0x07/0x80` (0..=255, reply byte 9), DPI `0x04/0x85`/`0x05` with a storage selector — `NOSTORE 0x00` the live value, `VARSTORE 0x01` also kept across power cycles (measured: a live write leaves the stored DPI; `dpi()` reads the live one) — a DPI write is skipped when that storage already holds it on both axes (the exit stores the offline DPI every time), poll rate `0x00/0x85`/`0x05` (`0x01` 1000, `0x02` 500, `0x08` 125 Hz). Every write is confirmed by reading it back. Per profile and mouse: `Profile.deviceMouse[deviceId]` (`mouseDpi` / `mousePollRateHz` / `mouseDpiStages`, all optional; pre-v5 flat fields are moved there for every built-in mouse on load, `migrate_mouse_settings`) are written into each connected mouse on every switch to that profile (`mouse_speed::apply_profile_mouse_settings`, own thread, called from `emit_profile_resolved_and_notify`) — the DPI live only (a switch per alt-tab must not wear the mouse's storage), and a switch superseded by a newer one (`PROFILE_SWITCHES`) is skipped; a profile without them leaves the mouse as it is. The Mouse tab's own DPI write (`set_mouse_dpi`) and the exit (`write_offline_profile`, the offline profile's DPI) store it. The first time a switch or a DPI step changes a mouse's live DPI / poll rate, the value it replaced is kept (`mouse_speed::Originals`, per device id, this run only — a restore process after a crash has none; a Mouse tab write forgets the field it set); the exit (`mouse_offline::restore_live_speed`) sets the offline profile's own poll rate and live DPI, else those originals — a V3 only its poll rate when a bank reselect follows (it sets the DPI). An unverified mouse gets no offline write and so no restore. A switch to a profile without mouse settings still supersedes an older queued switch, and a switch thread does nothing once the exit began. On every full scan the guard reads the battery of every present model, not only the one it guards (`poll_batteries`; a sleeping mouse keeps its last reading, an unplugged one drops out; a mouse whose read got no answer is asked again every tick and its first answer emits `mouse_battery` even when the level is unchanged, so the device cards stop saying "not answering" within one tick): `last_batteries` gives the tray tooltip one line `V3 Pro 100% · V2 9%` (`NativeModel.short_name`: Windows cuts the tooltip at 64 characters), `last_battery_percent` the corner badge — the mouse used last (`note_device_used`: any move or click of a catalog mouse, seen through raw input on the `system_events` window — `RIDEV_INPUTSINK`, device path → `device_catalog::model_for_path`, looked up only when the reporting device changes — or a button the capture dispatched, by the control's config device), else the lowest — drawn by `tray_badge.rs` with `Settings.showBatteryInTray`, and each change emits `mouse_battery` `{ model, percent, low }`; `low` is set below 10 % at most once per 24 h per mouse, remembered across restarts in `mouse-battery-warned-<device id>` (unix seconds) next to the config, with an OSD bubble naming the model.
- DPI stage actions (`MouseActionKind::DpiUp` / `DpiDown`) use the resolved profile, read actual live DPI, and choose the next higher/lower configured speed without wrapping or changing saved startup DPI. Writes are live-only (`set_dpi(..., false)`), serialized by the existing device lock and read-back verified. Missing stages and HID failures are explicit localized errors; live picker tests pass the profile ID and run blocking HID work off the async runtime.
- Mouse snapshot (`get_mouse_settings`): reads DPI, poll and battery independently under the existing device lock. Missing values serialize as null, never defaults. Device-open failure returns a snapshot; only exact `NOT_CONNECTED` is disconnected, all other failures are unavailable. Setters preserve their own read-back verification and return partial snapshots after success; failed confirmation remains an explicit error with no automatic retry.
- Device report (`get_device_report`, `open_device_report_issue`): `VendorDevice::probe_report` is read-only on any model, verified or not — Windows version, identity (VID:PID, interface), firmware (`0x00/0x81`), mode, DPI, raw poll code, battery (never the serial number — the report is public), then the raw 10-byte `0x02/0x8c` record of every button id that answers on layer 0, plus its layer-1 record (~20 s, holds `DEVICE_LOCK`). The Mouse tab's "Help verify" button (unverified + connected models) copies it and opens the `device_report.yml` issue form (`.github/ISSUE_TEMPLATE/`, label `device-report`); the report travels through the clipboard, never the URL. This is how a model gets its button table and moves to `verified` (plan `plans/multi-device/plan.md` §3.6 step 5-6).
- `get_device_report(detail)` accepts `summary` or `full`; absent detail preserves the full scan. Summary reads the common header only and returns application/Windows metadata even when open fails. It never scans button records, copies to clipboard or opens GitHub. Both modes omit serial/HID paths and all profile data.
- Offline profile (`mouse_offline.rs`): **one planner for every model**, `mouse_offline::plan(config, model, profile)` → per-control/layer decisions; `records()` extracts the `OfflineRecord`s; the onboard mouse's live session stores them in profile 1 while Sidearm runs, `live_overlay::write_offline` into the V3's banks. Enabled own `Offline` / `OfflineHypershift` bindings override layers 0/1 independently; unsupported firmware actions and `disabled` get the inert signal. Without an own binding, layer 0 uses standard and layer 1 uses hypershift, else standard (not the own layer-0 assignment); a left click under a right-button settings trigger remains a right click unless it has an own offline-hypershift assignment. `write_offline_to` writes two or more mice on scoped threads side by side (each model has its own device lock), one mouse on the calling thread. Models differ only by catalog data: `NativeModel.plain_left_modifiers` (the V3: plain records with the standard HID mask, never the turbo record; the V2: Shift/Alt shortcuts as the turbo `KeyTap`, a modifier-only hold with the right-hand bits) and the transport (the inert signal is consumer usage 0 on every model (`mouse_offline::BANK_SILENT_USAGE`: never one of Sidearm's signals — those made a bank of silent buttons look like Sidearm's own bank and, in a profile the mouse plays — offline, or a V2 power cycle before its live map is back — woke Sidearm's live actions; an unbound native button keeps its plain mouse button); an unbound control's layer 1 gets the inert signal in the V2's profile 1, a bank keeps its record). Only a key with modifiers or bare modifiers (HID usage from `hid_usage_for_vk`, usage 0 = modifiers held alone) or a plain mouse button (wheel up/down included: records 9/10, the wheel's factory value) bound as a plain press can live in a record; text, macros, launches, menus, per-app profiles and a binding with a `DoublePress`/`TriplePress`/`Chord` `trigger_mode` (the firmware fires on every press; `Hold` is what a live key record does) get the inert signal, never the old record. The trigger (`LiveSpec.firmware_trigger`, else the settings trigger among the native buttons) gets `OnboardAction::Hypershift` (category `0x0c`) when the profile has a playable hypershift binding or any enabled own offline-hypershift binding; the profile button is never written. The profile is `offline_profile_id(config, in_effect)`. **Onboard mouse (V2, stage 2, `plans/v2-ram-signals/plan.md`)**: profile 1 keeps the offline profile for good and Sidearm's signals live only in its live map (profile 0). Measured 2026-11-20 (`mouse_memory::tests::v2_flash_vs_ram_probes`): a profile-0 write leaves profile 1 alone; a profile-1 write plays at once (loaded into the live map); the live map survives sleep and `SET Normal`; a power off/on loads profile 1 into it. So its live session stores the offline profile (`live_overlay::store_onboard_offline` → `mouse_offline::store_onboard_offline`: records — `write_record` skips one already in place — and the profile's own DPI; skipped when it holds what this run stored, `onboard_offline_key` in `STORED`) before it writes the live map at start, and, when a config change queued a new one (`schedule_bank_store` → `ONBOARD_STORE`), on its next tick — after waiting for no button held — then repairs the live map the write replaced. A sleeping mouse is retried by the session; an exit, a kill or a restorer never writes it (`write_offline_to` and its `mouse-offline-failed` queue only name bank mice; an older queue naming the V2 is dropped) — the exit only puts its live speed back (`restore_onboard_speed`), and a stopped session's restored live map plays profile 1. A power cycle while Sidearm runs reads as drift (every record back to its original) and the session rewrites the map. **Bank mouse**: a mouse that did not answer anywhere in the exit's write (a record, its DPI, a bank reselect — `is_no_response`) is listed in `mouse-offline-failed` and the whole profile is retried; any other refusal is only logged (retrying it every 2 s would wear the storage). The next start turns a left `mouse-offline-failed` into the `offlineNotStored` notice; no mouse at all leaves neither. Wheel tilt has no onboard record (all ids 0x00..0xff scanned on both layers, 2026-10-17): the firmware plays tilt itself on layer 0, so tilt under firmware Hypershift (horizontal scroll) is lost without Sidearm — a known limit, not a bug.
- Vendor HID exchanges are serialized process-wide: a `VendorDevice` holds `DEVICE_LOCK` for its whole life, because a reply is fetched by a separate `GET_REPORT` and two concurrent users (guard tick + an IPC restore) read each other's replies — measured as a bogus "mode 0x01" and a false "rewritten" report. Open it, do the work, drop it; never hold one while opening another.
- Vendor HID (`mouse_memory.rs`): the collection is opened with **no** requested access rights and a sharing mode (Razer's driver holds it — GENERIC rights fail `ERROR_ACCESS_DENIED`), the feature buffer is 91 bytes for report id `0x03`, `VendorDevice::open_connected()` opens the first `CATALOG` model found and the device then takes its transaction byte, slots, native buttons, DPI range and poll codes from that model (config-side helpers still assume `NAGA_V2_HYPERSPEED` until the config names its model), and a write is only trusted when the mouse echoes it (`SET` → two `GET` → retry). The registry keeps leaves of devices no longer present (another USB port, a re-paired dongle): `open_first` tries every matching leaf (the consumer reader uses it too). A command reply counts only when it echoes the request's class and command (`reply_matches`; Razer's driver shares the report from another process) — otherwise the command is resent; status `0x04` (`NO_RESPONSE`, `is_no_response`) is a mouse that did not answer. The **slot** query (`0x02`/`0x0c` slot payloads with the `0a 02 0c 01` marker, no longer used) cannot cold-read: a `GET_REPORT` answers only with what the previous `SET_REPORT` stored. The **command** class does answer honestly and is what the guard reads: `class 0x00 / cmd 0x84` returns the device mode (`0x00` Normal = the firmware emits the onboard records; `0x03` Driver = Razer's driver maps the buttons instead) and `class 0x02 / cmd 0x8c` with `[profile=1, button, layer=0, …]` returns the stored record at reply bytes 11..=14 (`category, modifier, usage`; a mouse-category `0x01` record carries the button number where a key record has its modifier). Its twin `class 0x02 / cmd 0x0c` with `[profile=1, button, layer=0, category, len, value…]` writes a record (`restore_native_button`, and key records for the slot-less top buttons `0x0b`/`0x0c`) — the slot path's "marker" `0a 02 0c 01` is this same header. On the V2 HyperSpeed key records carry a HID modifier mask, written as Ctrl `0x01`, Win `0x08`, **right** Shift `0x20`, **right** Alt `0x40` (`modifier_bits`): that firmware never plays the left Shift `0x02` or left Alt `0x04` bit, alone or combined — measured 2026-10-27 at the Raw Input level, every other bit arrives. Limit: on a layout with AltGr (Russian) Windows adds Ctrl to the right Alt, so a stored `Alt+X` plays as `Ctrl+Alt+X` there. Records Synapse stored with `0x02`/`0x04` only ever played through Razer's driver mode, never from onboard memory. The **turbo** key record (category `0x0d`, `[0d, 04, modifier, usage, period_hi, period_lo]`) does play the left Shift and Alt with the standard mask (measured, Raw Input): the V2's offline profile writes a shortcut with Shift or Alt as `OnboardAction::KeyTap` — a turbo record with `KEY_TAP_PERIOD_MS` (10 s), i.e. one tap per press (`0xffff` played nothing) — so Alt+F4 works in any layout. A turbo record cannot hold: a modifier-only hold keeps the plain record with right-hand Shift/Alt. thumbs are bare `F13`..`F24`, the top buttons `Alt+F23`/`Alt+F24`; only `F13`..`F24` targets are ever written. **Signal kind**: by default a key button's live record is a consumer record — category `0x0a`, `[0a, 02, usage_hi, usage_lo]` — and its press reaches the capture helper as a HID report, never as a key (`capture_backend/consumer.rs`). A file `onboard-key-signals` next to the config (`KEY_SIGNALS_FILE`, read at startup into `set_consumer_signals`) selects `F13`..`F24` instead; the Mouse tab switches it live (`set_key_signals` creates/removes the file, flips the flag and restarts capture, which rewrites the live maps; it returns when that is done, and a stopped runtime stays stopped). `get_native_model` reports the mode as `consumerSignals` (`null` for a model without the consumer path). The record payload bytes 9..14 are `button_id, layer, 0x02, len, modifier, hid_usage`; `layer` is `0x00` on the slot path (`0x01` plays only under the firmware Hypershift and is written through `write_record`) and `modifier` is the HID mask above (`0x00` for a plain `F13`..`F24`).

- Connected mice: `mouse_memory::present_models()` lists the catalog models whose vendor interface Windows reports present (`CM_Get_Device_Interface_ListW`, no device traffic). `VendorDevice::open_onboard()` opens the connected onboard-path mouse (guard, offline profile, onboard IPC), `open_for_device(device_id)` the mouse of a config device (Mouse tab IPC: `get_native_model`, `get_mouse_settings`, `set_mouse_dpi`, `set_mouse_poll_rate`, `get_device_report` take an optional `deviceId`), `open_model(model)` one model, `open_connected()` any. `list_native_mice` returns the connected models' `NativeModelInfo` (with `deviceId`, `banks`). Each catalog model has its own device lock (`DEVICE_LOCKS`): one receiver is one exchange at a time, two receivers work in parallel.
- `src/system_events.rs`: a hidden top-level window for two broadcasts Tauri does not pass on, and for mouse and keyboard raw input (which catalog mouse is in use, for the tray battery badge, and which of its keys/buttons are held, `live_overlay::note_input`). `WM_DEVICECHANGE` (debounced, compared by connected model) emits `native_mice_changed` and restarts capture, so the live maps follow the mice actually plugged in; the frontend reloads the config when a new mouse's device is missing (loading seeds it). `WM_ENDSESSION` (shutdown, restart, logoff) runs `shutdown_mouse` — the same once-per-process exit as a quit (the second caller waits for the first, so the process never ends mid-write). A quit never runs it on the main thread: tray Quit, the admin relaunch, a test run's `quit` file and any other `ExitRequested` (prevented until done) go through `request_exit(source)` — logs `[system] exit requested (<source>)`, hides every window, puts the closing text in the tray (`show_exiting_in_tray`), runs `press_log::flush` + `shutdown_mouse` on the `exit` thread while the event loop keeps pumping (on the main thread it froze the window and tray 3-36 s, and every worker needing the main thread hung until the capture join gave up), then `app.exit(0)`; `RunEvent::Exit` still calls it as the fallback and finds it done. Each step logs `[system] exit step `<name>`: <ms> ms`, then `exit work done in <ms> ms`. Order: set `is_shutting_down` (from then on no press is dispatched, `capture_backend`), `mark_exiting`, stop capture (restores every live map: `live_overlay::stop_sessions` restores them on a thread of their own), `onboard_guard::wait_tick` (up to 5 s for a guard tick that began before — the tick holds `TICK` from its shutdown check on — so no tick puts signals over the offline profile), `wait_idle` (up to 30 s for every session — a reload's included — so a mouse stuck in a HID call cannot hang the exit; a config reload hands its stale sessions to the same thread, and a new session's worker waits — as long as it takes, without blocking whoever started it — for the previous session of that mouse to end before it claims `ACTIVE` and writes (a session stopped while still waiting never clears its predecessor's flag) — two never share a mouse's rollback file or `ACTIVE` flag), then store the offline profile; with `mouse-offline-failed` left a restorer is spawned. A Sidearm killed or crashed never restores and stores no offline profile: the V3 then plays Sidearm's silent signals, wheel included, until its profile button reloads a bank, and the V2's thumbs keep Sidearm's signals. So every Sidearm starts a **watchdog** at setup (`mouse_restore::spawn_watchdog`): `Sidearm.exe --spawn-watchdog <config dir> --watch <pid>` relaunches itself as `--restore-live-maps <config dir> --watch <pid>` and ends, so the watchdog's parent is gone and Task Manager's "End task" (which takes Sidearm and its capture helper together — measured 2026-11-10 on the notebook's V2: no restorer ran and the thumbs stayed silent) leaves it running. It also leaves Sidearm's job object: `spawn_detached` breaks away, and where the job allows no breakaway (`cargo run`'s, so every dev rebuild — measured 2026-11-14: the watchdog died with the app and the mice kept Sidearm's signals) it is created under the shell (`spawn_under_shell`, `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`: the child takes the parent's job and token — not elevated, which the restore does not need). It waits for that pid to end (a pid that ended without its clean exit first gets every modifier released — `input_synthesis::release_all_modifiers`: killed mid-shortcut, Sidearm left Ctrl down for every app); `Sidearm.exe --quit` (`QUIT_ARG`, through the single-instance plugin → `request_exit`; with no Sidearm running it starts none, `main.rs`) is how scripts stop it cleanly; a clean exit's last step writes `sidearm-clean-exit` with its pid (`mark_clean_exit`), and then the watchdog quits, otherwise it continues as the after-crash restore below (logged in `restore.log`). As a second line, a capture helper (same exe, `--capture-helper`, given the config dir in its init line) whose stdin closes without the `EXIT` line a stop writes first starts a detached, hook-free `Sidearm.exe --restore-live-maps <config dir> --after-crash` (`mouse_restore::restore_live_maps_main`) and exits at once; `--after-crash` makes it queue the offline profile (`offline_profile_id(config, None)`: the fallback for `@active`) in `mouse-offline-failed` when no exit did, so it is stored like an exit would. It logs to `restore.log` in Sidearm's log folder (`init_restore_log`, env_logger; there is no Tauri log plugin in it): a restore process's start moves a log over 1 MB to `restore.log.1` (never mid-run — the e2e run reads it from an offset); in the retry loop a line the previous round logged already is left out (`Rounds`: a sleeping mouse fails the same way every 2 s), with `still waiting for a mouse to answer (N tries, M min)` at most every 10 min; every end, early ones included, logs `[restore] process <pid> done: <why>` (its start `[restore] process <pid> started`); the `--spawn-watchdog`/`--spawn-restore` brokers open the log only to record a failed spawn. That process waits up to 15 s for `Local\Sidearm-app` (held by every running app from `run()` — `claim_app` keeps a handle even when an exiting Sidearm still holds it, measured 2026-11-11: a Sidearm started during an exit that waited on a sleeping V2 ran without it, and the restorer kept both mice for good) to disappear (still there = Sidearm is alive, quit — before taking any mutex, so a live Sidearm is never paused), takes `Local\Sidearm-live-map-restore` (one restorer at a time), then retries `live_overlay::restore_orphaned` — and, while `mouse-offline-failed` names a profile (first line) and the mice that slept (one device id per line), `mouse_offline::retry_offline_profile` — only those mice, so one that took the profile is not rewritten every retry; a pending mouse switched off keeps waiting — (an exit whose mouse slept spawns the same process) — every 2 s while a mouse sleeps (every minute after 30 min), until the work is done or a Sidearm starts — never giving up, so a mouse that sleeps for hours is not left silent; an HKCU `RunOnce` value (`SidearmRestoreMice`, `--spawn-restore`, which starts it with `--after-crash`) is registered by every Sidearm at start (`spawn_watchdog`) and removed by its clean exit (`mark_clean_exit`), so a power loss or a crash of Windows, which takes the watchdog along, is restored at the next logon; a waiting restorer registers it as well and removes it once the mice are restored, only while no Sidearm runs (a running one owns it); the logon broker puts it back when a Sidearm already runs (a logon task can start Sidearm before Windows runs `RunOnce`, which deletes the value it runs). One value name for every exe: the last Sidearm to start owns it. While the restore mutex exists a starting Sidearm leaves the mice alone (`live_map_restore_running`: live sessions wait, the guard counts as not running), so two processes never talk to one receiver. Both mutexes get an explicit DACL (authenticated users, `create_mutex`): with the default one an elevated Sidearm's mutex is invisible to a non-elevated process; `mutex_exists` also counts an access-denied mutex as present, so no check fails open.
- `src/live_overlay.rs` (module `mouse_memory::live_overlay`): reversible live `profile=0x00` maps for every model with a `LiveSpec`. `live_models(present)`: every verified model with a live path — the V2 too, alone or not (stage 2: its signals live only there, profile 1 keeps the offline profile). `software_hypershift(present, live, config)`: the mouse hook's trigger is on while an onboard-path mouse without a live map is connected, none is, or a live map takes its layer from it (`software_layer(config, model, present)`: the settings trigger a native button of a model without a firmware HyperShift button, with `hypershiftTap` — the V2 beside the V3 — or an onboard model that is the only verified mouse — the V2 alone, as on its old onboard path; its map writes the trigger as its plain mouse button and no layer-1 records, because the firmware's Hypershift swallows the quick press; beside the V3 without `hypershiftTap` each mouse's firmware holds its own HyperShift, one software trigger cannot tell two mice apart). `overlay()` builds one model's targets and consumer signals: key buttons always, extra and native controls only for an enabled non-disabled action (or the setup check), the settings trigger (or the model's firmware button) as `Hypershift` on both layers (unless `software_layer`), left click → right click under a right-button trigger, `F13`..`F24` key records in keyboard-fallback mode (a key button without one is an error). `configure(config, present)` adds the config device of a connected verified `LiveOverlay` model once, with its controls and one reserved alias per control and layer and no bindings (copying assignments is the frontend's `device-transfer.ts`). A `Session` per model writes the map, keeps a rollback file (`<device_id>-live.json`, matched to the receiver by VID/PID so another USB port still restores; the 2026-11-08 rc names are migrated), checks one record every two seconds (two mismatching reads = drift), repairs only differing records (a record read as the same foreign value twice is adopted as the new original, a single odd read is not), never writes a live record while a button of that mouse is held (`write_bank` → `wait_released`, at most 5 s: `HELD` per model, fed by the capture helper's reader lines and by raw keyboard/mouse input from the mouse's own collections in `system_events` — rewriting a record under a held button strands the old record's key, measured as a stuck Shift+Enter), restores on stop (a record read as something else twice is the user's change and stays; a single odd read does not drop it) and reports `is_active`/`is_ready`; a snapshot that would take Sidearm's own signal (reserved consumer usage, `F13`..`F24`) as the original takes a native button's plain record instead, or keeps it with a warning; HID presses of an active model are dispatched only once it is ready (`events_allowed`). An onboard model's session first stores the offline profile in its profile 1 (see Offline profile). A failed rollback is logged and the original write error returned. `live_map_ready(deviceId)` tells the setup wizard whether a mouse's buttons reach Sidearm (a live map verified, or an onboard mouse connected).
- Onboard banks (`LiveSpec.banks`, the V3's stored profiles, class `0x05`: count `0x80`, inventory `0x81`, active `0x84`, select `0x04`; `parse_banks` checks they agree). `Profile.device_slots` (`deviceSlots`, device id → bank 1–5; Banks are written in the background 5 s after the start selected Sidearm's bank and after the config last changed (`schedule_bank_store`, re-checking generation/shutdown/ownership under the device lock; only while the mouse has Sidearm's own bank or a managed hybrid bank — on the live-map path the playing bank is the user's and writing it would replace the live map; no live speed change, no bank select) and at exit (`write_offline`), which never writes the bank playing: when a bank to write plays and the mouse has Sidearm's own bank, that one plays during the write (`off_the_playing_bank` after `wait_released`; writing the playing bank changes the live map at once and strands a held button's key), and the bank comes back afterwards — the exit's own bank, or the one that played (reconciling `ACTIVE_LIVE_BANK` on any error path and replaying desired profile after background store completes); it — and a later background store — skips the writes when this run already stored the same (`store_key`: the banks, each planned bank's mode, records and DPI; the exit then only puts the speed back and selects the bank);: every linked profile into its bank, or — with one bank and no link — the offline profile; an unlinked bank that Sidearm wrote earlier (a rollback file exists) gets its own records back, others are left alone. Each written bank has a rollback file (`<device_id>-bank-<n>.json`) and read-back verification, and gets the profile's own DPI for that mouse (the V3 keeps a DPI per bank and switches to it with the bank; `set_dpi_in(bank, …)`, storage byte = bank, measured readable with `0x04/0x85`); afterwards the offline profile's bank (else the one that was playing) is selected. The live map is restored record by record by its session before that, also at exit: leaving it to the reselect failed on the real V3 (2026-11-14 — only the records restored first played, the rest stayed Sidearm's silent signals; reselecting the bank already playing reloads nothing). A live record that holds Sidearm's own signal when a session snapshots it (its rollback file lost) takes the playing bank's record as its original, else a native button's plain record (test `a_live_map_left_with_sidearms_signals_takes_the_playing_banks_records_as_originals`). `apply_bank` keeps a record Sidearm wrote earlier whose target stays the same and that still reads as it (no restore-then-rewrite; test `rewriting_a_bank_ends_as_restoring_it_first`); every other one goes back first. **Sidearm's own bank** (consumer signals only, plan `plans/sidearm-bank/plan.md`): a session claims the first free slot (`05:02`, `create_bank`; the firmware fills it with factory records and leaves the live map alone, measured 2026-11-15) unless the mouse has one already — found by content, every key button holding Sidearm's own signal on layer 0 (`sidearm_bank`), so it follows the mouse to another PC. `claim_sidearm_bank` → `sync_sidearm_bank` makes it the base bank's records (`base_bank`: the offline profile's bank, else the one playing; a record Sidearm stored there for use without it plays its original instead) with the live targets over them, only differing records written (under a held button it waits, `wait_released`: the playing bank is the live map), plus the base's DPI. The start then selects it (one command; the live map is never written, an older live rollback file is dropped) and writes `<device_id>-in-sidearm-bank`; the profile button taking the mouse to another bank is **offline mode** (logged, nothing repaired) until the Sidearm bank plays again. Stopping selects the base bank (`leave_sidearm_bank`), unless the profile button already left it; `restore_orphaned` does the same for a killed Sidearm while the marker is there (the base from the config on disk, else the user's first bank). Sidearm's bank is left out of `banks()`, `bank_plan`, `exit_bank` and `store_banks` (`user_banks`). No free slot or keyboard-fallback signals: the live-map path below. `05:03` unassigns a bank (measured): `release_sidearm_bank` (IPC, Mouse memory's "Return slot"; `get_sidearm_bank` tells the UI the slot) restarts capture with `keep_off_sidearm_bank` set, so the session leaves the bank and runs on the live map for the rest of this run, then unassigns the slot; the next start claims a free slot again. On the live-map path Sidearm never switches banks while it runs: the firmware would replace the live map. When the user does (the profile button), the session watches the active bank every tick and repairs the live map at once. A bank never gets the turbo key record (`NAGA_V3_PRO.plain_left_modifiers`: a plain key record with the standard HID mask, the form Synapse stores — Alt+F4 = `02 02 04 3d`; a turbo record repeats while the firmware thinks the button is held, and the V3 fired a stored Alt+F4 turbo every 10 s on its own, Sidearm closed, measured 2026-11-10). Measured 2026-11-10 with `live_overlay::tests::v3_plain_left_modifiers` (interactive): the V3 plays a plain record's left Shift `0x02`, left Alt `0x04` and right Shift `0x20` as such, and right Alt `0x40` as AltGr (LCtrl+RAlt) on the Russian layout — so a right-hand Alt is wrong for the V3. The V2 HyperSpeed drops the left bits, so its onboard path keeps the turbo tap. What a bank gets comes from the shared planner (`mouse_offline::plan`, see Offline profile). A failed live-overlay offline store from a sleeping mouse leaves `mouse-offline-failed` like the onboard path.

## Work Guidance

- `unwrap`/`expect` only where a preceding branch guarantees safety; never on user/hardware-controlled input.
- Offline exit writes run on a detached `mouse-offline` worker with a 30 s wait limit, including device-lock waits and HID calls. Snapshot the present verified targets (onboard mice and configured live-overlay mice) before starting it; queue their device ids after the profile in `mouse-offline-failed` and pass the same targets to the writer. Completion replaces/removes the marker through the normal writer; an absent target stays pending until it returns, while a permanent command refusal is logged without retry. On timeout or worker failure, return so the existing restorer can take over after the app releases its mutex. Never join a stalled worker on exit. Restorer retries remain synchronous in their separate process.
- `write_record` compares the meaningful raw record bytes before skipping a write and after writing, including record length and the turbo period. Live poll-rate and DPI restoration are independent attempts; a failed poll-rate read still allows DPI restoration.
- Battery cache pruning uses every present model before selecting silent mice for a light poll. Keep the independent `last_battery_scan` while an offline-profile restore is pending.
- Menu views retain full action text for search and clip only the rendered detail. `View.maxHeight` is the opening monitor's physical work-area height; the page converts it by its current DPR, scrolls the rows, and keeps the highlight visible. `ViewItem.text` / `textChildren` enable text-only pick modes for rows and tip children; Copy without text is always consumed without execution.
- The watchdog holds `Local\Sidearm-watchdog-<pid>` (scoped in fake mode) while it waits; `spawn_watchdog` waits up to 5 s for it off the setup, retries once, then logs that no watchdog runs. The `main-thread-watch` thread posts a task every 5 s and logs when the main thread has not answered for 10 s and when it is back (a hang leaves the process alive, so nothing else notices). Still frozen at 45 s and a fresh task unanswered for 10 s more (time asleep is no hang), `hang_recovery::recover` writes a minidump `hang-<unix>-<pid>.dmp` into the log folder (newest 3 kept), frees the modifiers, starts a new Sidearm with `--relaunched` (`mouse_restore::spawn_relaunch`; it waits for this one's `Local\Sidearm-app`) and exits with code 3, so the watchdog restores the mice as after a kill. Not under a debugger. Read a dump with the build's symbols: `cdbX64 -z <dmp> -y E:\Scripts\Sidearm\symbols\<version-date>` (release builds put function names and lines in `sidearm.pdb`, `debug = "line-tables-only"`; `build_portable.ps1` keeps the exe + pdb of the last 5 builds there).
- **Never hold a lock across a Tauri window or tray call off the main thread.** Getters (`hwnd()`, `scale_factor()`), tray/menu setters (`set_icon`, `run_item_main_thread!`) and window creation wait for the main thread, and sync `#[tauri::command]` fns run on the main thread — one of them waiting for the same lock deadlocks both. Decide under the lock, then act on the main thread (`run_on_main_thread`) and re-check there: `cheatsheet::cancel_then`, `update_tray_icon` → `settle_tray_icon`; `restart_capture_with` rebuilds the tray only after releasing the `RuntimeController` lock.
- Cheat-sheet cancellation, pending page readiness, timer draws and native shows share one lifecycle lock: cancellation clears pending/drawn state at once, so stale timer/layout callbacks cannot reopen it; the hide runs on the main thread and is skipped when a newer hold drew meanwhile.
