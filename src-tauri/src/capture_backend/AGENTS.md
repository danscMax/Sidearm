# src-tauri/src/capture_backend — Keyboard + mouse capture

## Purpose

The low-level input hooks and the Razer-encoding detector: turns raw key events into encoded button signals (F13–F24), imposes the software Hypershift layer, suppresses/replays modifiers, dispatches actions, and keeps holds alive.

## Ownership

- `windows.rs` — `WH_KEYBOARD_LL` hook, `WH_MOUSE_LL` hook (software Hypershift) plus its `hyper-inject` right-click thread and liveness check, encoding-chord detection, modifier buffering, hook-health probe, the capture worker + bounded event channel, foreground watcher.
- `consumer.rs` — the consumer-signal reader (helper process): opens the config model's consumer collection (`mouse_memory::consumer_collection_paths` via `open_first`, shared access next to Razer's driver), overlapped `ReadFile`, reopens every 2 s after the dongle sleeps or is unplugged (releasing every held button first), and translates reports into the keyboard hook's own lines. Pure parts (`held_usages`, `Translator`, `repeat_timing`) are unit-tested.
- `mod.rs` — `process_encoded_key_event`: profile resolution, action lookup, dispatch, hold/release handling.
- `linux.rs` — Linux capture (not the primary target).

## Local Contracts

- In Sidearm's own foreground window, only direct `dpiUp`/`dpiDown` mouse actions bypass the input-action block. Shortcuts, clicks, text, menus and sequences remain blocked; tests pin this narrow exception.

- This is a hard-latency path (the LL hook callback has a ~200–300ms system budget): no heavy work, allocations, or blocking in the hook callback. Per-keystroke work already got audited/optimized — do not regress it. The mouse hook is worse: it sees every mouse move, so non-button messages must bail on a single compare.
- **Never call `SendInput` from inside the `WH_MOUSE_LL` callback** — measured, not theoretical: an injection issued there blocks for the full `LowLevelHooksTimeout` (~1000 ms), because the injected event has to travel the very hook chain whose thread is still inside the callback. Every other input event queues behind it, so the pointer freezes in ~1 s batches (two per translated click: down + up) until Windows silently drops the hook. The same call from the hook thread *outside* a callback, or from another thread while no callback injection is pending, costs 0.4–4 ms. The callback therefore only enqueues; the `hyper-inject` thread injects. (The keyboard hook is unaffected: its in-callback injections measure ~1 ms.)
- **Software Hypershift**: this device's firmware only ever emits the standard-layer record as long as no button holds a firmware Hypershift record (measured — with the right button stored as Hypershift `0x0c` the firmware swallows it and emits the layer-1 records itself; `onboard_guard.rs` puts the trigger back), so the layer is *imposed* by the helper, not read. The mouse hook holds `HELPER_HYPER_ACTIVE` while the trigger button is held, swallows that button (it is a pure modifier), and turns the left button into a right click. A scroll tick carries no encoded key to stamp — the firmware turns buttons, never the wheel, into `F13`..`F24` — so the hook emits the encoder mapping of a wheel direction the user bound on the hypershift layer and swallows the tick (`wheel_capture_action`; an unbound direction keeps scrolling natively, which is why the parent tags a wheel direction as such only when a hypershift binding for it exists). The keyboard hook stamps every match it emits with `HS:` while the state is held, and the parent turns that into `EncodedKeyEvent.is_hypershift` at parse time. Stamping must stay at capture time — reading the state at dispatch time races a fast trigger release. The translation decisions live in the pure `hyper_mouse_action` and `wheel_capture_action` (unit-tested); the hook only applies their verdict.
- **The mouse hook needs its own liveness check**: Windows drops a `WH_MOUSE_LL` hook silently after a low-level-hook timeout, and the keyboard probe can never see that (it only reports a dead *keyboard* hook) — the trigger would stay dead for the rest of the session. Any mouse callback proves life; pointer movement (≥ `MOUSE_HEALTH_MOVE_PX`) with no callback means the hook is gone; a tagged 1-px probe settles the parked-pointer case. A dead verdict reinstalls the hook (which also clears a stuck held state) and a failed install keeps retrying.
- The helper's message pump is the labeled `'pump` loop: every exit (WM_QUIT on stdin close, a failed rehook, a closed stdout) leaves it with `break 'pump` — a plain `break` left only the inner `PeekMessage` loop, so a stopped helper lived on without hooks until the parent killed it 5 s later, on every stop and reload.
- Helper diagnostics: the helper's stderr is piped into the parent log as `[helper] …` (it used to go nowhere, so a dropped hook or a panic left no trace). Helper death (stdout EOF not caused by `stop()`, which sets `HelperHandle.stopping` first) restarts capture (`schedule_helper_restart` → `crate::restart_capture`, after 1 s / 5 s / 30 s, skipped when a reload or stop/start replaced that helper meanwhile — `HELPER_GENERATION`; a failed restart stops the runtime and emits `runtime_stopped`); a fourth death within 10 min, or a failed restart, gives up: runtime warning + the `helperLost` mouse status (toast with a restart action). A successful spawn clears `helperLost` and `buttonsUnreadable` (a new reader reports again; none starts in F13..F24 mode). Hook-path diagnostics ride the match stream instead — `DEBUG:…` lines the parent logs at `debug`, and `NOTE:…` lines it logs at `info` for hook events with no action dispatch to be inferred from (the translated Hypershift click) — so the hook itself never formats into a log sink.
- The trigger comes from `Settings.hypershift_trigger` (`HYPER_TRIGGER_CONTROLS` in `config.rs`) and must be a button the mouse still reports as a native mouse button: a button whose onboard record was rewritten into a keystroke never reaches the mouse hook. Absent/`none` = no mouse hook is installed at all.
- The parent's helper-line parser feeds every unstamped key-down to `onboard_guard::note_signal`: an `F13`..`F24` with Ctrl/Shift/Win is an encoding Sidearm never writes, i.e. the firmware's own Hypershift fired, and it triggers an immediate guard check. Our own wheel ticks carry `HS:` and are excluded.
- **Side buttons (mouse 4/5)** stay native X buttons on the wire (their onboard records are plain mouse buttons, so back/forward work without Sidearm) and no keyboard registration can match them. The parent tags a `mouse_4`/`mouse_5` encoder mapping as a `ButtonCapture` only when that layer has an enabled binding; the mouse hook then swallows the X press and emits that mapping (`side_button_capture`: hypershift encoding while the trigger is held, else the standard one, stamped `HS:` when held so the resolver falls back), remembers it per button, and emits the matching `UP:` on release. The hook is installed when the trigger is set or any side button is captured (`mouse_hook_wanted`). An X button that is itself the trigger stays the trigger.
- **Remote Desktop**: while `GetSystemMetrics(SM_REMOTESESSION)` is set (`is_remote_session`, re-read per button event — a console session can be taken over by RDP and handed back), the mouse hook treats the trigger as off and clears the held state: RDP delivers the client's clicks as ordinary input, so swallowing the trigger killed every remote right click. Side-button capture keeps working.
- The mouse hook only swallows the trigger button, LMB-while-held, a bound hypershift wheel tick, and a captured side button; every other message — including our own `INTERNAL_SENDINPUT_EXTRA_INFO` injections — returns `CallNextHookEx` untouched.
- A press while Sidearm's own window is foreground (`window_capture::OWN_WINDOW_REASON`) is resolved and emitted as `control_resolved` (the UI highlights it) but never dispatched: our injected keys would otherwise hit the window's own shortcuts (`Delete`/`Backspace` clear the selected binding, `1`–`4` switch tabs, `Enter` opens the editor). Key-ups still run, so a hold started elsewhere releases.
- The mask/probe key is VK 0xE8 (`VK_PROBE_KEY` / `VK_MASK_KEY`); the hook passes it through and it is not a modifier.
- The event channel is bounded and drops on full by design (a stalled consumer must not block the producer). Prefer draining releases promptly so holds don't stick.
- Razer encoding window (~10ms) vs modifier replay buffer (~20ms) are tuned constants — change only with real hardware measurements.
- An elevated foreground window (UIPI blocks our input) emits `elevated_foreground_blocked` `{exe}` once per app (`should_notify_elevated`), and only while Sidearm itself is not elevated.

- **Consumer signals** (default on the V2 HyperSpeed): the parent passes `mouse_memory::consumer_signals(config)` — `(usage, encoded key)` for every key button's standard-layer mapping — in the helper init (`consumerSignals`); a non-empty list starts the reader. A press emits that encoded key exactly as the keyboard hook would (`F13`, stamped `HS:` from `HELPER_HYPER_ACTIVE` at read time), a release `UP:`, and a held button gets `REPEAT:` on Windows' own keyboard delay/rate (`SPI_GETKEYBOARDDELAY`/`SPEED`) because the device does not repeat. Report = id `0x02` + little-endian `u16` usages up to the first zero (`02 00 00` = all released). The reader tells the parent whether it can read the collection with `STATUS:buttonsUnreadable` / `STATUS:buttonsReadable` lines (→ the `buttonsUnreadable` mouse status). The device reports changes only, so a mouse that powered off mid-press (dongle still present) never sends the release: a hold silent for `HOLD_GIVE_UP_AFTER` (10 min) is released. It cannot be asked instead — measured 2026-10-27: `HidD_GetInputReport` on this collection answers "nothing held" while a button is held. The helper's stdout is locked **per drain**, never for its whole life, because the reader thread writes to the same pipe. The `F13`..`F24` registrations stay: they serve the rollback switch and a mouse still holding old records until the guard rewrites them. Known limit (unmeasured on hardware): the `HS:` stamp reads the mouse hook's state from another thread, so a thumb pressed within a few ms of the trigger may resolve on the standard layer. Measured on hardware (2026-10-27): the consumer report carries one usage, so two thumbs pressed together arrive one after the other (the second press releases the first) — a hold on one thumb ends when another thumb is pressed.

- Capture start reads the connected mice (`mouse_memory::present_models`) and builds one live map per mouse that needs it (`live_overlay::live_models`); a map that cannot be built is a runtime warning (`capture.liveMapFailed`), never a silent empty map. The helper starts one consumer reader per mouse (`ReaderInit`: catalog index, signals, whether the layer comes from the software trigger). Every reader line carries `M<catalog index>:` (`consumer::reader_prefix`), so the parent knows the mouse: its presses get the backend tag `hid:<device id>` and are dropped while that mouse's live map is not ready; its `STATUS:` lines are tracked per mouse and `buttonsUnreadable` is set while any of them reports it. An onboard-path mouse without a live map keeps the old single reader with the software trigger's `HS:` stamp. The software trigger is off (`firmware_hypershift`) when every connected mouse holds HyperShift in its firmware. Keyboard registrations skip a device whose encodings arrive another way: a live map in consumer mode, or a live-only mouse that is not connected (its aliases must not grab real shortcuts).
- On config save, keep each mouse's live session if its target records are unchanged; stale sessions are restored before their replacements write. All sessions are asked to stop at once and then joined, so two mice restore in parallel. An intercepted V3 vertical wheel tick without an active assignment is replayed as scrolling. In Sidearm's own window intercepted vertical wheel ticks also scroll.
- The setup check (`set_input_capture_mode(.., checkExtraControls)`) temporarily includes every extra control in the standard layer of the live maps and suspends execution. Signal lookup and firmware targets share one check-mode snapshot. Leaving the check restores the normal map without storing the test records in an onboard bank.

## Work Guidance

- Prefer linear scans over hash maps for the small hotkey/action sets (cache locality beats hashing at these sizes on this budget).

## Verification

- `cargo test` + `cargo clippy ... -D warnings`. Behaviour that depends on real hardware/UAC needs a manual check on the device — including the trigger button and the LMB→RMB translation, and that holding the trigger keeps the pointer smooth (no ~1 s stutter) so the mouse hook is never injected from inside its own callback.
