# src/components — UI components

## Purpose

All React components: mouse visualization, modals (action picker, app-mapping, confirm, error, presets, Synapse import), profiles/settings workspaces, command palette, onboarding, toasts, context menu, and shared primitives.

## Ownership

- `shared.tsx` — the canonical primitives: `ModalShell`, `ModalHeader`, `ModalFooter`, `Toggle`, `Notice`, `CloseButton`, `SettingRow` (settings line: title + hint left, control right; `.setting-row` in `App.css`). Reuse these; do not fork new modal/toggle/row visuals. Settings screens live in `.settings-shell__content`, capped at 920px.
- `mouse-visual/` — legend cells + columns (`LegendCell` is the keyboard-accessible control button that spreads `useControlInteractions`).
- `settings/` — settings panels + `SettingsShell`.
- `ProfilesWorkspace.tsx` is the one screen per profile and device: a profile strip on top (the edited profile, its app rules as chips — click edits the rule, right-click opens the rule menu, "+ App" creates one — and the "All rules" toggle that shows every profile's rule cards for drag reorder/move), `DeviceCards` (one card per device: a built-in mouse shows battery / DPI / poll rate / the profile's slot, read on mount and on mouse events, never on a timer; "not connected" otherwise; user devices show their button count), and for a built-in mouse three tabs: Buttons (search, layers, visualization, profile export/import/transfer), Performance and Mouse memory (`MouseWorkspace` with `deviceId` and `section`). There is no separate "Mouse" workspace mode.
- `MouseWorkspace.tsx` renders one mouse's tab. "performance": the readings with the `showBatteryInTray` switch, the edited profile's own DPI / poll rate for this mouse (`Profile.deviceMouse[deviceId]`; saved to the profile, also written to the mouse at once when that profile is the runtime one), the side-button signals switch. "memory": the onboard slots (one pill row per bank, `setProfileDeviceSlot`, filled from `getOnboardBanks`) and `offlineProfileId` as pills (profile written into the mouse on exit; empty = the fallback profile, listed first as "<name> (fallback)"; `OFFLINE_PROFILE_ACTIVE` = the one in effect at exit).
- Mouse readings are separate from saved profile settings: show nullable values honestly and one consolidated warning with field details. Refresh on mount/manual request and existing battery/DPI events, never by an added timer. Coalesce events, invalidate older responses and dispose late subscriptions on unmount. Seed own settings only from available DPI/poll. Summary diagnostics are available on verified models too, shown locally and copied only on explicit request; the old full verification/GitHub flow remains separate.
- DPI is one control in the existing Sensitivity SettingRow: shared PillTrack presets and an explicit localized Manual segment plus the always-available numeric input/Apply. Manual only selects input mode and focuses the existing field; it never saves or writes a DPI. Focusing/editing the field selects Manual; choosing a numeric preset exits Manual. Mode resets when the edited profile changes. Both controls edit the same saved profile DPI; actual device DPI stays in the readings card. Opening never creates stages. An explicit numeric choice/application saves up to five stages, preserving configured values; a new manual value replaces the selected saved stage only when the list is full. There is no separate stage form or second numeric input. Never reassign mouse buttons for UI verification.
- `icons.tsx`, workspace shells, and the modal components.
- `SynapseNotice.tsx` consolidates Razer process/driver/mapping warnings into one persistent bottom-right `Toast` card. Closing the Razer engine is explicit and warns about shared modules; the startup checkbox defaults off and an undo is available for this computer/user. Technical recovery leads to a physical HyperShift test, not a success claim. Process snapshots recover state for late-opened windows; subsequent Razer launches renew the warning. Ordinary toasts share the bottom-right stack without replacing the conflict card.
- Delegated to child: `action-picker/` (the per-ActionType editors).

## Local Contracts

- The portable migration prompt shows feedback while a choice is applied. Starting fresh keeps the loaded config and does not reload it.

- Modals use `ModalShell` (Escape, focus-trap, focus restore). Popovers/menus use `useDismissable` + `useListKeyboard` for keyboard operability.
- Icon-only buttons carry an `aria-label`; search/text inputs carry an `aria-label` (placeholder is not an accessible name).
- Reusable CaptureRow and ChipEditor require an explicit localized `ariaLabel` on their actual inputs, including chip entry after the placeholder disappears. A labelled wrapper/group alone does not name a nested field. Existing visible captions may supply the same localized text through aria-label.
- Ordinary input/textarea/select controls opt into the canonical `.input`/`.field` recipe; compact dimensions may remain local. Process search, device rename, capability status and log filters reuse the shared fill/border/focus. ChipEditor, CommandPalette and TokenTextarea keep their composite-editor visuals and narrowly scoped canon-guard exceptions.
- Class names and colours come from `App.css` tokens. Do not reuse a class for a different purpose — e.g. `.field__hint` is a 16×16 "?" badge, not a text-hint class; visible help text uses `panel__muted`.
- The DPI number field carries the canonical `.input` class inside the existing `.input-suffix` unit wrapper. Reuse the shared input recipe (also used by global-shortcut capture); do not introduce a separate DPI field visual.
- Dynamic positioning/sizing goes through the CSSOM (CSP: no inline `style={}`).
- Capture form values in the event handler before passing a config updater. Deferred updaters must not read event.target/currentTarget later, after React restores a controlled input.

## Work Guidance

- Signals (`encoderMappings`, e.g. `F13`) of the built-in Naga are Sidearm's own transport codes, written into the mouse by the backend: never show or edit them there (`isBuiltinControl` in `lib/onboard-mapping.ts`). The action picker hides `SignalCaptureField` and never saves a mapping for them, Diagnostics hides the signal chip + verification workflow (`signalsHidden`) and shows the verification session only when a user device exists, the tester picks "button · layer" instead of a typed code, and hotspot tooltips drop the code. User devices keep every signal UI — the recorded signal is how a button is identified. Onboarding writes the mouse (`restoreOnboardControl`) instead of teaching Synapse/F-keys.
- An unassigned control is labelled "Native action" (it passes through to the device/Synapse default), distinct from the "OFF" pill for an explicitly-disabled binding.
- `ActionPickerModal` shows the global HyperShift role before profile actions, with an explicit all-profiles scope and replacement/removal warning. The role edits `settings.hypershiftTrigger`, never adds an `ActionType`; existing actions survive a role transfer. Native action removes the selected slot's binding. A new action/binding is created only on Save, with collision-safe IDs; opening/cancelling must not change the config. The five native trigger choices share `NATIVE_HYPERSHIFT_TRIGGERS` with general settings; encoded key buttons and scroll ticks remain unsupported as triggers.
- Built-in mice are drawn from their `DeviceLayout` (`lib/devices.ts`): views and tab labels, hotspots and legend columns, the firmware HyperShift button, the side-view note, the extras the setup wizard checks. `MouseVisualization` takes the layout of the device shown and never tests for a model; the HS badge comes from `hypershiftControlId` (the settings trigger, or the layout's firmware button). A device card selects an independent config device for editing and updates the sidebar. Switching tabs never restarts capture or writes the mouse. User devices render `GenericDeviceView` (legend grid + optional photo with click-to-place hotspots); `AddControlModal` learns generic buttons via DOM key capture; device photos are served as `data:` URLs via `read_device_image`.
- Every reading and write of `MouseWorkspace` goes to its `deviceId` (the selected card); the profile's DPI / poll rate / stages edited there are that mouse's own (`Profile.deviceMouse`, `setProfileMouse`).
- `DeviceTransferModal` ("Copy from another mouse", shown with two built-in mice) previews and applies `lib/device-transfer.ts`: source and target mouse, current or all profiles, keep or replace occupied buttons, with the left-out bindings and why. Importing a profile file puts bindings for controls this config lacks onto the mouse shown (`retargetImportedBindings`) and says how many found no place.
- Onboarding (`onboarding/OnboardingWizard.tsx`) follows the connected mice (`listNativeMice`, `native_mice_changed`): one mouse is set up directly, two ask which, none says so and goes on. Steps come from `wizardSteps(mouse, layout)`: the onboard write only on the onboard path, the button and extras checks only for a verified model, then administrator windows and a try-it step. The welcome step checks Razer Synapse (`getSynapseStatus`) and can close it (`recoverFromSynapse`, startup change opt-in, unchecked). The check waits for `getLiveMapReady(deviceId)` and after 15 s offers Check again or skipping; it counts presses by the chosen mouse's own controls (`thumbOf`) and its `hid:<device>` stream, standard and held layers separately with the trigger's name in the instructions. Execution stays suspended during the checks. Restart-as-admin saves the step (`onboardingStep`) so the elevated instance resumes there. Capture is not auto-started before setup finishes: setup starts it after its Synapse check.
